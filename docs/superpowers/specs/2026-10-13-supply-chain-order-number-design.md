## 1. 目标、依据与范围

总订单号 `SC_01M4SJJ9QN2TWZV16MHSRQZ96V`、发给华昇的单号 `BILL_01M4SJJ9SHWKPARFPWPJCQW39Q` 来自现有 `BusinessNoGenerator` 的“受控前缀 + 26 位大写 ULID”规则，符合原详细设计 §4.1。此次调整业务可见订单编号，使日期直接可读、格式为纯数字，并由 MySQL 持久化流水保证分配不重复。

参考仓库为 `/Users/mac/codespace/cardshop`。实际普通下单规则在 `cardShop-admin/src/main/java/com/ruoyi/web/mc/service/impl/McOrderServiceImpl.java#generateOrderSn`、`McOrderV2ServiceImpl.java#generateOrderSn` 与 `ruoyi-common/src/main/java/com/ruoyi/common/utils/OrderUtils.java#generateOrderSn`：14 位日期时间 + 随机补位 + Redis 当日递增序号，后两段通常合计 10 位。`OrderNoUtils` 另有随机数字、UUID 片段等规则，不作为本设计的下单规则依据。cardshop 只作为实现参考，不在本轮修改。

新规则覆盖上线后创建的：

- `sc_order.order_no`：CARD、O2O、INSTORE 三种场景共用的供应链总订单号。
- `sc_b_order.billno`：标准履约发给供应商的稳定业务单号，包括华昇 `outOrderSn`。

`b_order_no`、受理回执、履约请求、路由轮次、操作、事件、Timer、资金引用编号、O2O/到店购场景明细及支付流水编号继续按各自既有规则生成。本轮不把所有业务编号切换为数字，不引入新的供应商重下或切换策略。

## 2. 编号格式与不变量

### 2.1 格式

新编号为 ASCII 十进制字符串，固定 24 位，无字母或分隔符：

```text
yyyyMMddHHmmss + RR + SSSSSSSS
    14 位       2 位    8 位
```

- 日期时间使用供应链 MySQL 会话的 `CURRENT_TIMESTAMP(3)`，会话时区统一 `+08:00`，语义为 `Asia/Shanghai`。复用现有 `SupplyChainDatabaseClock`，禁止数据库取时失败后回退 JVM 时间。
- 日期作用域和时间前缀必须来自同一次取时；一次分配批次复用该时间，不分别获取日期和时间。
- `RR` 为 `00`～`99`，固定两位随机数字。它只增加编号变化，不承担唯一性、加密、身份鉴权或防猜测职责。
- 随机段由服务端生成，格式化显式使用 `Locale.ROOT` 和ASCII数字；不以部署机器的默认语言改变数字字符。测试可替换内部随机源，外部调用方不能选择该值。
- `SSSSSSSS` 为当日共享流水的固定八位十进制表示，范围 `00000001`～`99999999`，左侧补零。

示例仅说明格式：总订单号 `202610131530274200000001`；对应履约尝试的商户单号 `202610131530277300000002`。

### 2.2 唯一性与容量

总订单号和 `billno` 在同一个供应链独立库共用一条每日流水，不按用途、供应商、场景或实例拆分。日期 + 固定流水段确定已分配编号的唯一身份；随机段取相同值也不会重号。八位流水的每日容量为 **99,999,999 个编号**，不是该数量的订单：标准受理通常消耗两个编号，O2O/INSTORE 总单通常消耗一个，未使用的预分配号码也计入消耗。

cardshop 的“随机补位 + 可变位数流水”不能完整照搬：随机 `123456782` + 流水 `1`，与随机 `12345678` + 流水 `21`，都可拼出尾段 `1234567821`。本设计固定两个段的宽度，避免这种拼接碰撞。

已提交分配的流水永久消耗，允许断号，不承诺连续或按最终订单提交时间严格递增；号码分配顺序也不等于业务成功顺序。容量耗尽明确拒绝新取号，不扩位、不回绕、不切回 ULID。编号日期表示**分配时刻**：分配后跨午夜才建单，编号仍保留原日期，不为了与 `created_at` 对齐重新取号。

### 2.3 业务身份

- 总订单号在创建总单时绑定，一个总单永久保持原号。
- 一个 B 端履约尝试绑定一个 `billno`，与总订单号分别分配；不得令 `billno = orderNo`。
- 华昇 `outOrderSn` 使用本地 `billno`，华昇返回 `orderSn` 保存为 `external_order_no`。远端编号按原字符串保存，不能按本地格式改写。
- 重试、QUERY、回调、CONFIRM、TAKE、Timer/Outbox 和进程恢复读取已持久化编号与冻结操作快照，不调用取号服务。
- 只有业务状态机允许创建全新履约尝试时才分配新的 `billno`；未知结果继续恢复原单，不能借本设计自动重下。
- 所有接口、JSON、Java DTO 和前端均使用字符串；禁止转为 JavaScript `Number`、浮点数或 JSON 数字。

## 3. 不新增连接池的方案比较与决策

| 方案 | 回滚与并发表现 | 代价与结论 |
| --- | --- | --- |
| **A：业务事务前独立短事务批量取号，提交后进入业务事务** | 取号提交后永久消耗；同一请求取号时不持有业务连接；业务事务不持有流水锁 | 需要调整编排边界、传递不可变预分配号码；可能产生断号。**本设计推荐** |
| B：流水更新加入建单事务 | 同一业务连接即可，但流水随业务回滚；每日流水行锁持有到整个业务事务结束 | 不满足原方案“已提交分配不随建单回滚复用”的目标，且每日共享锁放大对路由、资金及其它场景的阻塞；不采用 |
| C：事务外持久化大号段，进程内缓存消费 | 持久化号段提交后不重发，业务内只消费内存号码 | 需要跨日切换、线程安全、重启丢号、耗尽处理及补段协调；补段仍必须移到业务事务外。无吞吐证据前不引入 |

用户否决的专用小连接池方案已撤回，不作为备选实施路径。也不在现有业务事务内调用共用池的 `REQUIRES_NEW` 取号：外层占用连接、内层再借连接，会增加连接饥饿风险。

采用 A，只使用现有 `supplyChainDataSource`、`supplyChainTransactionManager`、`supplyChainSqlSessionFactory` 和 `SupplyChainDatabaseClock`。不新增连接池、数据源、事务管理器、线程池或定时补号任务，不以提高现有池大小作为本功能成立的前提。

本方案消除**取号新增的嵌套借连接**，不宣称整个下单链零连接饥饿：现有 `CurrentSupplyEligibilityReader` 等仍有独立事务，其容量与预算约束继续适用。取号自身也可能因现有池繁忙而超时，应沿既有预算与异常边界失败。

## 4. 存储、短事务与故障边界

### 4.1 新增流水表

由供应链 Liquibase 新增 `sc_order_no_sequence`，不修改旧迁移校验和，不访问其它模块库，不建立物理外键。字段契约如下，后续 DO 注释与 DDL COMMENT 必须一致：

| 字段 | 类型与约束 | COMMENT 语义 |
| --- | --- | --- |
| `sequence_date` | `DATE NOT NULL`，主键 | 订单编号流水所属日期，Asia/Shanghai |
| `last_value` | `INT UNSIGNED NOT NULL`，CHECK 0～99999999 | 已提交分配的当日订单编号最大流水，初始为0 |
| `created_at` | `DATETIME(3) NOT NULL` | 订单编号流水行创建时间，Asia/Shanghai |
| `updated_at` | `DATETIME(3) NOT NULL` | 订单编号流水行最后更新时间，Asia/Shanghai |

同日只有一行；所有用途共享。跨日创建新行，旧行永久保留，不配置按日清理、重置或回收。日期行无业务自增主键暴露问题，流水表不提供管理端人工占号、改号、重置或删除接口。

### 4.2 分配算法

`OrderNoAllocationService` 的公开编排入口必须先确认调用线程不处于实际数据库事务，也未持有供应链绑定连接；发现误用立即失败，**不得挂起外层事务后继续取号**。由该入口通过显式绑定 `supplyChainTransactionManager` 的 `TransactionTemplate` 开启一次短事务，避免同类自调用导致注解失效。

本期只接受封闭的用途集合：单个总订单号，或标准受理的一对“总订单号 + 供应商商户单号”。调用方不能提交日期、流水、随机数或最终号码；未来若业务状态机新增独立供应商尝试的创建能力，届时单独评审独立商户单号用途，不在本期预留可调用的重下入口。

短事务步骤：

1. 使用 `SupplyChainDatabaseClock.now()` 获取一次数据库时间，得到日期与完整时间前缀。
2. 原子确保该日期行存在；首日并发创建由日期主键收敛。使用参数化 XML 的 MySQL `INSERT ... ON DUPLICATE KEY UPDATE` 仅保证行存在，不重置现有 `last_value`，不用 `INSERT IGNORE` 吞掉其它错误。
3. 对日期行 `SELECT ... FOR UPDATE` 当前读。优先使用既有 MyBatis Plus 方法引用行锁写法。
4. 检查剩余容量是否够本批次，再按固定用途顺序分配连续流水。标准受理一对号码按总订单号在前、`billno` 在后；不足两个则整批失败，不只分配一个。
5. 持久化新的 `last_value` 和同次取时的更新时间，构造固定格式结果。更新使用 Lambda 条件绑定日期和原 `last_value`，影响行数必须为1。
6. 提交成功后才把不可变预分配结果交给外层。最终业务事务开始时，取号连接与日期行锁均已释放。

短事务只访问流水表和数据库时间，不读写回执、订单、报价、账户、账本、Outbox 或 Timer，也不外呼。Mapper 不新增注解 SQL；必要的 upsert 方言写入 XML，其余查询/更新用 Lambda。

### 4.3 失败和恢复

- 分配事务明确回滚且未返回号码：该批分配未成立，流水可由下一次成功事务使用；不能将事务内未提交的局部值记为已分配。
- 分配已提交、但格式返回、进程或业务创建随后失败：流水已消耗；不回减、不放回池。未使用号码为正常断号。
- 分配提交结果不确定（例如提交时连接断开）：本次不返回号码、不继续建单；可能已消耗的流水保留。下次重新按权威行分配，不把本地记忆值当成可复用号码。
- 锁等待、死锁、数据库时间获取或连接预算失败：事务结束、连接按既有机制释放；本期不新增递归或无限取号重试，不自动降级成随机号或 ULID。
- 容量耗尽使用新的稳定错误符号 `ORDER_NO_CAPACITY_EXHAUSTED`，语义为“当日订单编号流水容量已耗尽”，按现有 `ServiceException` 业务拒绝合同返回；数值编码在实现时从供应链错误码段分配。事务入口误用或流水更新影响行数异常是基础设施不变量破坏，使用系统异常；数据库与提交故障保留 cause，不能伪装为商品不可售或供应商拒单。
- MySQL 时钟回拨到历史日期仍使用保留的同日流水行，只推进、不重置。若整库恢复到旧快照、流水行被人为删除或备份与真实已发出单号不一致，不能宣称自动保持全球唯一；恢复前停止新取号，恢复已分配高水位并核对外部已发出单号后再开放。未落单但已经消耗的流水不能仅靠扫描订单表完整还原。

现有 `sc_order.order_no` 全局唯一键和 `(supplier_id, billno)` 唯一键保留为业务落库防线。正常一致数据库下分配器保证跨用途不重复；一旦命中编号唯一冲突，按数据完整性故障阻止建单，不用自动换号掩盖序列回退或异常写入，不把任意唯一冲突误当业务幂等命中。

## 5. 事务外编排与幂等

### 5.1 总体顺序

```text
认证与基本参数校验
  → 既有身份/幂等准备事务（结束并释放连接）
  → 已有结果则按原合同回放
  → 确需继续创建：现有池短事务分配号码（提交并释放连接）
  → 新的业务事务内按原锁顺序重新核验幂等、状态、准入与资金
  → 使用预分配号码原子创建订单及关联对象
  → 提交后返回真实持久化结果 / 触发既有后续执行
```

预探测是减少无效取号的优化，不授予创建权，不取代业务事务中的锁、指纹比较和唯一约束。号码分配成功只表示预留了身份，不能写成“订单创建成功”或“供应商下单成功”。号码不改变请求指纹、报价键、项目永久受理键、限购/限频键或路由排序。

### 5.2 标准履约 CARD

已有 `RechargeFrequencyAcceptanceCoordinator` 强制事务外调用。扩展这个协调入口：保留 Facade 的 claim、报价首冻和命令准备顺序；只有 `executeAcceptance=true` 才进入预分配，普通已受理/终态回放不取号。

协调器在最终受理事务前为本次创建准备两个号码，并通过独立内部值对象传给 `FulfillmentAcceptanceLifecycle.accept` / `acceptDirectProjectOrder`。该值对象不进入外部请求、请求摘要、永久报价或 target 加密内容，不由项目调用方指定。

Lifecycle 内先锁回执、核指纹和状态；若竞争期间另一请求已接受，则返回已持久化快照，不能使用预分配号码覆盖获胜订单。仍需创建时，原样保留 receipt→LST→SKU→quote→当前准入与资格复核等既有顺序，仅把原 SC/BILL 取号位置替换为读取本次预分配值。`b_order_no` 仍独立生成，`billno` 按原创建流程写入 BOrder、operation/checkpoint 与查询参数。

现有队列身份唯一键竞争的有限重试，在已确认整个业务事务回滚后可复用**同一次协调调用持有的这对号码**；它们未提交绑定给其它订单且未对外发送，复用不意味着返还流水。禁止重试中再次进入取号事务，禁止捕获任意异常或提交不确定后盲目重跑。新一次外部请求若确需续跑创建，可新分配一对，之前号码成为断号。

若预分配期间发生故障，但同参竞争者已经完成受理，协调器可通过一个已结束取号事务之后的短只读入口核对回执及完整请求指纹，只有可信已接受结果才回放；未完成则传播原故障。不能通过无条件调用 `replay(receiptId)` 掩盖异参、拒绝或系统故障。该规则保证已完成订单的可信回放不新增对流水分配可用性的依赖。

### 5.3 O2O 与 INSTORE

两个场景目前都在 Lifecycle 业务事务内生成 `SC_` 总单号，需增加场景应用层的事务外创建协调入口；Facade 委托它，不直接访问 Mapper。场景协调器与取号服务都禁止在外层实际事务中调用。

- O2O：把已有按渠道交易号的幂等准备/回放判断提取为短事务探测，保留现有“已启用用户绑定校验→已有交易探测→金额一致性校验”顺序；确需创建时预分配一个总订单号，再进入 `createPaymentPreparation` 的原子建单事务。当前 `replayExistingPayment` 校验金额，不比较完整请求指纹，本轮不趁编号改造增加或声称已有完整指纹比较。收银台调用继续在业务事务提交之后执行。
- INSTORE：按 `(channelCode, tradeId)` 探测已有流水，严格沿用已有作用域、金额和回放规则；已有结果直接回放。新创建路径预分配一个总订单号，进入 `createPaymentOrder` 后重新核查订单头与支付流水。若事务内发现可复用已有订单头，继续使用其已持久化总单号，未使用预分配号成为断号；不能因号码已分配绕过现有 1:1 流水约束。
- 并发预探测都未命中时允许分别取号，最后仍由业务永久键决定唯一订单；沿用/补齐对应场景的**已知业务键**竞争收敛，不能通过捕获所有 `DuplicateKeyException` 盲回放。
- 已有结果的探测必须复用原合同的权限与身份校验，不额外收紧或放宽。INSTORE现有流程先探测支付流水，回放核金额及订单头上的project/profile/buyerUser身份，未命中才进入用户和商户绑定校验；提取时保持这个顺序。取号失败后的只读竞争回放复用同一场景校验，不能只凭业务键返回订单。

所有业务事务仍完整覆盖总单、明细、资金、状态审计和 Outbox。前置取号不提前冻结资金、消费订单业务状态或调用远端。此次只重排编号分配，不改动商业准入判定、付款、履约或退款语义。

### 5.4 接口与代码边界

- 公共 HTTP/RPC 请求字段、签名版本、路径和返回字段保持原合同；`orderNo` 仍是稳定、不透明的字符串。
- 新增内部号码值对象和专用分配服务，不改变通用 `BusinessNoGenerator.next(prefix)`，不将新增数据库调用隐藏在其内部。
- CARD、O2O、INSTORE 所有总订单创建入口必须通过协调器进入；旧 Lifecycle 直接调用入口不能提供一个在事务内临时取号的兼容回退。
- `routing.domain` 不依赖 Spring/MyBatis；Facade 不依赖 DAL；供应链不访问 `system_*`/`member_*`。新的内部号码传递不穿过 Feign、不新增外部注册。
- 替换三个生产 SC 创建点和标准履约 BILL 创建点，并以架构/源码门禁防止新增生产订单入口绕过专用分配器。

## 6. 历史兼容、页面与日志

存量总单、BOrder、回执结果快照、路由主体、资金引用、operation/checkpoint、Outbox、Timer、华昇请求及回调关联不改号。上线后新建使用数字规则，历史 `SC_`/`BILL_` 继续查询、履约及回放；PROCESSING 历史回执尚未建单时按新规则创建，已创建的历史单始终沿用原号。

现有 `order_no VARCHAR(32)`、`billno VARCHAR(64)` 可容纳 24 位数字，保留原列宽与唯一键，不收窄旧列。读取、查询、路径参数、回调和重放校验不新增“只能是数字”限制；只有新生成格式的纯逻辑格式器严格要求24位。

## 7. 性能、连接预算与锁顺序

每次待创建的标准受理只进行一次批量取号事务，取两个号码；不引入进程大号段缓存。取号事务持有每日流水行锁的时间只包含日期取时、行初始化/锁定和更新，不覆盖商品、报价、资格复核、资金或外呼。

同一请求的预探测、取号、最终建单分段顺序运行，进入取号前必须释放准备阶段的连接；进入业务事务前必须释放取号连接。业务事务完全不访问流水表，防止业务表锁与流水锁形成反向等待。所有入口都使用既有预算数据源，不通过底层裸池或自己创建 JDBC 连接绕过预算守卫。

不调整全局 Hikari、网络超时、预算路由与锁等待配置来掩盖本功能问题。真实 MySQL 并发门禁验证流水锁等待、借连接数和事务释放；同时回归已有嵌套资格 Reader 及限购门禁。只有实测瓶颈成立后才另行评审持久化号段优化，不在本轮宣称任意吞吐已达标。

## 8. 自动化与联调门禁
