## 1. 目标、依据与范围

总订单号 `SC_01M4SJJ9QN2TWZV16MHSRQZ96V`、发给华昇的单号 `BILL_01M4SJJ9SHWKPARFPWPJCQW39Q` 来自现有 `BusinessNoGenerator` 的“受控前缀 + 26 位大写 ULID”规则，符合原详细设计 §4.1。此次调整业务可见订单编号，使日期直接可读、格式为纯数字。Redis负责日常原子自增和号段内消费，MySQL负责不同实例号段不重叠的持久化分配及业务落库唯一约束，不再每取一对号码就更新数据库流水行。

参考仓库为 `/Users/mac/codespace/cardshop`。实际普通下单规则在 `cardShop-admin/src/main/java/com/ruoyi/web/mc/service/impl/McOrderServiceImpl.java#generateOrderSn`、`McOrderV2ServiceImpl.java#generateOrderSn` 与 `ruoyi-common/src/main/java/com/ruoyi/common/utils/OrderUtils.java#generateOrderSn`：14 位日期时间 + 随机补位 + Redis 当日递增序号，后两段通常合计 10 位。`OrderNoUtils` 另有随机数字、UUID 片段等规则，不作为本设计的下单规则依据。cardshop 只作为实现参考，不在本轮修改。

新规则覆盖上线后创建的：

- `sc_supply_chain_order.order_no`：CARD、O2O、INSTORE 三种场景共用的供应链总订单号。
- `sc_b_order.billno`：标准履约发给供应商的稳定业务单号，包括华昇 `outOrderSn`。

`b_order_no`、受理回执、履约请求、路由轮次、操作、事件、Timer、资金引用编号、O2O/到店购场景明细及支付流水编号继续按各自既有规则生成。本轮不把所有业务编号切换为数字，不引入新的供应商重下或切换策略。

## 2. 编号格式与不变量

### 2.1 格式

新编号为 ASCII 十进制字符串，固定 24 位，无字母或分隔符：

```text
yyyyMMddHHmmss + RR + SSSSSSSS
    14 位       2 位    8 位
```

- 编号时间使用本次Redis消费脚本内的 `TIME`，将返回的Unix秒与微秒转换为 `Asia/Shanghai`。正常取号无需先查询MySQL时间，也不依赖各JVM的默认时区。持久化业务时间、准入、有效期、账本、Timer等继续使用 `SupplyChainDatabaseClock`；本条只调整编号显示时间来源。
- 日期作用域和时间前缀必须来自同一次脚本取时。脚本检查Redis时间在当前号段日期的上海零点闭开区间内；跨日时不消费旧段，返回时间供事务外协调器准备新日期号段，再次执行脚本。以成功消费那一次的Redis时间形成前缀，不混用先前取时。
- `RR` 为 `00`～`99`，固定两位随机数字。它只增加编号变化，不承担唯一性、加密、身份鉴权或防猜测职责。
- 随机段由服务端生成，格式化显式使用 `Locale.ROOT` 和ASCII数字；不以部署机器的默认语言改变数字字符。测试可替换内部随机源，外部调用方不能选择该值。
- `SSSSSSSS` 为当日共享流水的固定八位十进制表示，范围 `00000001`～`99999999`，左侧补零。

示例仅说明格式：总订单号 `202610131530274200000001`；对应履约尝试的商户单号 `202610131530277300000002`。

### 2.2 唯一性与容量

总订单号和 `billno` 在同一个供应链独立库共用每日**号段预留高水位**。数据库分配给各实例的区间互不重叠，Redis在实例专属区间内递增消费；用途和场景不拥有可从1重启的独立号码池。日期 + 固定流水段确定编号身份，随机段相同也不会重号。

八位流水的每日容量为 **99,999,999 个可预留流水位置**，不是该数量的订单。标准受理通常消费两个，O2O/INSTORE总单通常消费一个；预留后未用、实例重启和故障弃用的整个区间也计入消耗。号码在本实例号段内递增，不能承诺多实例间按请求时刻全局连续或单调。

唯一性范围是共享同一MySQL预留高水位的供应链发号域。Redis的env/scope键隔离不让24位数字在多套独立库间自动唯一；发布前须核对供应商商户号的真实唯一作用域，不能让卡管、其它独立库或环境未经协调地共用同一个供应商商户订单号域。本期不跨库查询或改造cardshop共享号池；如实际需要跨系统共用同一商户编号域，须先单独确认统一号域方案再上线。

cardshop 的“随机补位 + 可变位数流水”不能完整照搬：随机 `123456782` + 流水 `1`，与随机 `12345678` + 流水 `21`，都可拼出尾段 `1234567821`。本设计固定两个段的宽度，避免这种拼接碰撞。

已提交预留的区间永久占用，未用部分也不转给其它实例，不因Redis键丢失或订单回滚回收。容量耗尽明确拒绝无法获得号码的新创建，不扩位、不回绕、不切回ULID；已有号段还有足够号码时可继续消费。编号日期表示**Redis消费分配时刻**：取号后跨午夜才建单，编号仍保留原日期，不为了与 `created_at` 对齐重新取号。

### 2.3 业务身份

- 总订单号在创建总单时绑定，一个总单永久保持原号。
- 一个 B 端履约尝试绑定一个 `billno`，与总订单号分别分配；不得令 `billno = orderNo`。
- 华昇 `outOrderSn` 使用本地 `billno`，华昇返回 `orderSn` 保存为 `external_order_no`。远端编号按原字符串保存，不能按本地格式改写。
- 重试、QUERY、回调、CONFIRM、TAKE、Timer/Outbox 和进程恢复读取已持久化编号与冻结操作快照，不调用取号服务。
- 只有业务状态机允许创建全新履约尝试时才分配新的 `billno`；未知结果继续恢复原单，不能借本设计自动重下。
- 所有接口、JSON、Java DTO 和前端均使用字符串；禁止转为 JavaScript `Number`、浮点数或 JSON 数字。

## 3. Redis参与方式、备选与推荐

| 方案 | Redis职责与数据库访问 | 故障防重边界与结论 |
| --- | --- | --- |
| A：共享日计数器INCRBY + 订单唯一键 | 取号只访问Redis，订单落库由MySQL防重 | 简单，但Redis计数器丢失/回退可能重发已取未落库的号码；唯一键不能证明“所有已发号永久不复用”。不作为当前可靠性目标的推荐 |
| B：Redis生成候选 + MySQL逐号登记 | Redis自增，每批号码必须先写永久占号表 | 可以严格登记成功后再返回，但每次仍需MySQL事务与逐号存储；可作为不接受号段断号成本时的备选 |
| **C：MySQL预留实例专属号段 + Redis原子消费** | 正常一次Lua取1或2号；只有首段、耗尽、换日或弃段后才申请数据库号段 | 配合单一实例所有权、本地返回高水位与不确定时弃段，处理Redis回退。减少数据库流水写入；代价是状态协调和断号。**用户已评审通过，进入本地实施** |

不采用额外Redis分布式锁串行化每次取号：Lua已提供消费原子性；锁失效或Redis数据回退也不能证明已发号不复用。Redis脚本可原子执行，脚本缓存丢失应按NOSCRIPT重新加载；这些都不等于持久化无损。[Redis Lua说明](https://redis.io/docs/latest/develop/programmability/eval-intro/)

Redis通常异步复制，WAIT也不把它变成强一致系统；主从切换仍可能丢已确认写入。AOF、复制与告警继续作为运维保障，但本设计的防重不能只建立在“已开启持久化”上。[Redis复制说明](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/)

用户否决的专用连接池方案继续撤回。正常取号不借MySQL连接；申请号段只使用现有 `supplyChainDataSource`、`supplyChainTransactionManager`、`supplyChainSqlSessionFactory`。Redis复用现有`RedissonClient`（§10.1落地选择）或既有`StringRedisTemplate`/连接工厂，不创建新客户端池。供应链已有旅通回调按需使用StringRedisTemplate，共享RedisTemplate的值序列化为JSON；计数器必须使用字符串/原生整数，不复用JSON值序列化。后续验证实际依赖装配与Redis服务版本，不因源码存在接口就声称线上条件已满足。

本功能不新增连接池、数据源、事务管理器、线程池或定时补号任务，不以提高现有池大小为前提；仍保留事务外编排。它消除取号新增的嵌套借连接，不宣称解决既有资格Reader等所有连接等待。

## 4. 号段、Redis算法与故障边界

### 4.1 MySQL永久预留与所有权

由供应链Liquibase新增以下两张表，均在供应链独立库，无物理外键，沿用全库utf8mb4/utf8mb4_0900_ai_ci，不修改旧迁移校验和。DO注释与DDL COMMENT一致：

| 表/字段 | 类型与约束 | COMMENT语义 |
| --- | --- | --- |
| `sc_order_no_sequence.sequence_date` | DATE主键 | 订单编号流水所属日期，Asia/Shanghai |
| `sc_order_no_sequence.last_reserved_value` | INT UNSIGNED，CHECK 0～99999999 | 已提交预留号段的当日最大流水，初始为0 |
| `sc_order_no_sequence.created_at` | DATETIME(3)非空 | 订单编号流水行创建时间，Asia/Shanghai |
| `sc_order_no_sequence.updated_at` | DATETIME(3)非空 | 订单编号流水行最后更新时间，Asia/Shanghai |
| `sc_order_no_segment.sequence_date` | DATE非空 | 订单编号号段所属日期，Asia/Shanghai |
| `sc_order_no_segment.start_value` | INT UNSIGNED非空，与日期组成主键 | 已提交预留号段的起始流水，含边界 |
| `sc_order_no_segment.end_value` | INT UNSIGNED非空 | 已提交预留号段的结束流水，含边界 |
| `sc_order_no_segment.owner_id` | VARCHAR(32)非空 | 号段独占分配器本次启动标识 |
| `sc_order_no_segment.created_at` | DATETIME(3)非空 | 订单编号号段预留记录创建时间，Asia/Shanghai |

号段CHECK要求 `1 <= start_value <= end_value <= 99999999`；记录不重写、不删除、不回收。全局区间不重叠由日期行锁下的高水位推进保证，不能仅靠区间起点唯一键证明。

一个运行中的Spring供应链容器仅有一个消费分配器，启动时生成新的ownerId；新容器、进程重启、分配器状态丢失都不从Redis或数据库恢复使用旧号段，必须申请新区间。数据库高水位确保区间唯一，ownerId用于所有权关联，不能以随机ownerId本身证明唯一性。

**每个号段只由分配到它的一个运行中分配器消费，不让多个实例共同消费同一段，也不向存活新实例转移旧段剩余号码。** ownerId、日期、起止值和Redis键绑定成不可变内部状态，外部请求不能提供。正常按段消费，实例间可并发；本实例采用有界等待的互斥保护消费、返回高水位和换段，不能并发执行同一段的多个Lua请求后仅靠回调更新高水位。

初始号段大小为1000个流水位置，作为本功能显式配置，允许2～10000；小于一次最大批次2的配置拒绝启动。正常默认一个完整段可服务500次标准双号受理，不意味着每日真实请求数达到了该值。数据库最后不足1000但足够本次批次时，可预留剩余区间；不足本批数量则拒绝预留。双号必须在同一段内同时消费，不能只返回一个；本实例剩余1个时如需双号，则弃用这一位置后申请新段。容量按预留高水位计算，不能借回收其它实例余号扩容。

### 4.2 申请号段的短事务

`OrderNoAllocationService.prepare` 先确认没有实际数据库事务、没有供应链绑定连接；误用立即失败，不挂起业务事务再借第二个连接。仅在无可消费本地段时，经显式绑定 `supplyChainTransactionManager` 的TransactionTemplate申请号段：

取号用途使用封闭内部枚举：`ORDER_ONLY` 消费一个总单号，`ORDER_AND_BILL` 按总单号在前、billno在后的顺序消费两个。调用方不传原始数量、日期、owner、scope、区间、floor或最终编号；未来独立商户单号用途随对应状态机另行评审，不在本期提供重下入口。

1. 首次没有日期状态时读取Redis TIME，转换为上海日期；跨日则用脚本返回时间确定待申请日期。此处只是申请目标，真正编号时间在消费脚本中再次校验。
2. 短事务用参数化XML upsert确保该日期行存在，不重置高水位，不用INSERT IGNORE吞其它异常；SELECT FOR UPDATE当前读日期行。
3. 根据配置段长和本批需求检查容量，推进 `last_reserved_value`，同时插入对应ownerId的永久区间记录。创建/更新时间使用SupplyChainDatabaseClock；事务内不调用Redis。
4. 查询/条件更新优先MyBatis Plus Lambda，影响行数必须为1；upsert等必要方言使用XML，不加注解SQL。
5. 短事务提交并释放连接后，才将区间作为本实例可消费状态，并安装Redis键。数据库提交结果不确定时不使用该区间，下一次申请新的区间；Redis安装失败不回减已提交高水位。

预留事务只访问号段/流水表及数据库时间，不访问回执、订单、资金、报价、Outbox或Timer。MySQL提交后Redis初始化可失败，这个间隙只形成弃用区间，不用跨系统事务把数据库已提交号段回滚。

### 4.3 Redis原子自增与回退保护

键格式为 `supply-chain:order-no:{env:scope:date:owner:start}:cursor`，`scope` 是部署配置的供应链独立库发号域，env/scope不能来自订单请求。单个Lua只访问这一显式KEYS键，hash tag包括段身份，可用于Redis Cluster；不跨槽访问动态拼出的其它键。

Redis保存绝对流水cursor。本地同时保存当前段 `lastReturnedValue`，初值为start-1；该值表示本分配器已经消费并承诺不再返回的最大流水，而非订单已提交数。Lua一次取1或2号，执行以下有限步骤：

1. TIME取Redis服务器时间，验证位于传入日期的上海零点闭开区间。跨日返回专用结果与时间，**不修改cursor**。支持TIME与写入同脚本的环境作为发布前置：本期验收Redis7及以上，实际版本未核实不得标记已通过。[TIME说明](https://redis.io/docs/latest/commands/time/)、[Lua复制模式说明](https://redis.io/docs/latest/develop/programmability/eval-intro/)
2. 检查批次数、起止区间、本地floor和现有cursor的类型/范围。缺键时以本地floor执行SET NX初始化；发现Redis值低于本地floor则只向上修复到floor，绝不降低已有更大值。高于end或非法值属于不变量故障，不继续发号。
3. 检查 `max(cursor, floor) + count <= end`。不足则返回段耗尽，不部分消费；足够则使用INCRBY原子取得本批最大流水。日期时间和分配结果在同一个脚本内产生。
4. 给键设置固定的日期结束后7天绝对过期点，用于状态清理，不把TTL当号段租约。脚本错误并无业务事务回滚承诺：任意写后异常按结果不确定处理，不能假设cursor未变。
5. 分配器在同一互斥范围内校验响应、先推进本地lastReturnedValue，再构造24位字符串并返回不可变批次。随机段仍由服务端生成；构造失败也不回减floor。

可明确判定的NOSCRIPT在未执行时按现有客户端支持重新加载/执行一次。其它Redis超时、断连、脚本写后错误、响应不确定或非法状态，**立即在本地永久弃用当前段，再释放互斥锁；不重试旧段、不在它上面猜测是否消费过。** 响应处理必须绑定发起调用的段身份；超时弃段后若有迟到结果，只做清理，不能返回旧段号码或修改新区间的floor。成功响应后曾返回的号由本地floor保护；状态丢失或进程退出后通过申请新区间保护。

这是三层分工：MySQL保证实例区间不重叠；Redis脚本保证本次范围检查和自增不被插入竞争；本地floor防止该独占段的Redis确认写回退。进程内锁只保护本地状态，不能取代MySQL的跨实例区间约束。也不新增逐订单SET NX占号键或永久去重Set，避免把Redis占号状态丢失误当成号码可重新使用。

### 4.4 故障边界与错误

- Redis缺键、删除或回退：运行中且状态完整的独占分配器可以在Lua内从本地floor向上恢复；其它实例不碰旧段。进程重启即申请新段，禁止从旧Redis cursor接着发号。
- Redis不可用或调用结果不确定：当前请求停止新建，当前段弃用；恢复后申请新段。**不自动切换MySQL逐号模式、JVM随机号或ULID**，避免混用两条发号轨道。已持久化订单的查询、可信回放和原单恢复不因新取号失败改号。
- MySQL暂不可用：已有已确认区间、Redis正常时可以继续生成号码；新区间申请失败停止新取号。但订单创建及资金仍需MySQL，这不表示系统能脱离数据库完成交易。
- 数据库预留明确回滚：未预留区间可重新参与未来成功预留；提交不确定则本实例不用该区间，已提交区间永久保留。
- 业务回滚、序列化失败或请求取消：已预留/已消费号不回收；队列身份已知回滚的有限重试可复用同次协调调用的号码，见§5.2。
- Redis时间回拨：切换日期需弃用本地旧段，按数据库该历史日期保留高水位申请新区间，不能重置为1。编号顺序不承担业务时间排序或准入语义。
- MySQL全库恢复旧快照或人为重置高水位：停止整个发号域的写实例取号，并弃用所有运行中本地段，再结合永久号段记录、备份与外部已发出事实恢复高水位；不从业务订单表MAX值或Redis残留值推导完整已预留集合。恢复后实例以新owner申请新区间，不能同时让恢复前的段继续消费。Redis恢复不会解决数据库权威记录回退。
- `ORDER_NO_CAPACITY_EXHAUSTED` 表示当日可预留号段容量不足，按既有ServiceException合同返回；具体数值从供应链错误码段分配。Redis、数据库、提交不确定、事务误用和号段不变量错误保留系统异常因果，不能映射成商品不可售或供应商拒绝。

保留 `sc_supply_chain_order.order_no` 全局唯一键和 `(supplier_id, billno)` 唯一键。正常区间分配与消费协议保证不重发，业务唯一键是最后落库防线；出现编号唯一冲突阻断建单并定位，不自动换号掩盖区间重用，也不把任意唯一冲突当幂等成功。

## 5. 事务外编排与幂等

### 5.1 总体顺序

```text
认证与基本参数校验
  → 既有身份/幂等准备事务（结束并释放连接）
  → 已有结果则按原合同回放
  → 确需继续创建：事务外由Redis原子消费1或2号
      （无本地可用段时先用现有MySQL池预留号段，提交并释放连接）
  → 新的业务事务内按原锁顺序重新核验幂等、状态、准入与资金
  → 使用预分配号码原子创建订单及关联对象
  → 提交后返回真实持久化结果 / 触发既有后续执行
```

预探测是减少无效取号的优化，不授予创建权，不取代业务事务中的锁、指纹比较和唯一约束。号码分配成功只表示预留了身份，不能写成“订单创建成功”或“供应商下单成功”。号码不改变请求指纹、报价键、项目永久受理键、限购/限频键或路由排序。

### 5.2 标准履约 CARD

已有 `RechargeFrequencyAcceptanceCoordinator` 强制事务外调用。扩展这个协调入口：保留 Facade 的 claim、报价首冻和命令准备顺序；只有 `executeAcceptance=true` 才进入预分配，普通已受理/终态回放不取号。

协调器在最终受理事务前由Redis一次消费两个号码，并通过独立内部值对象传给 `FulfillmentAcceptanceLifecycle.accept` / `acceptDirectProjectOrder`。正常消费不查询MySQL时间或流水表；需要新段才先运行独立预留事务。该值对象不进入外部请求、请求摘要、永久报价或 target 加密内容，不由项目调用方指定。

Lifecycle 内先锁回执、核指纹和状态；若竞争期间另一请求已接受，则返回已持久化快照，不能使用预分配号码覆盖获胜订单。仍需创建时，原样保留 receipt→LST→SKU→quote→当前准入与资格复核等既有顺序，仅把原 SC/BILL 取号位置替换为读取本次预分配值。`b_order_no` 仍独立生成，`billno` 按原创建流程写入 BOrder、operation/checkpoint 与查询参数。

现有队列身份唯一键竞争的有限重试，在已确认整个业务事务回滚后可复用**同一次协调调用持有的这对号码**；它们未提交绑定给其它订单且未对外发送，复用不意味着返还流水。禁止重试中再次进入取号事务，禁止捕获任意异常或提交不确定后盲目重跑。新一次外部请求若确需续跑创建，可新分配一对，之前号码成为断号。

若取号期间发生故障，但同参竞争者已经完成受理，协调器可在号段预留事务已结束、Redis调用已收敛且相关本地互斥已释放后，通过短只读入口核对回执及完整请求指纹，只有可信已接受结果才回放；未完成则传播原故障。不能通过无条件调用 `replay(receiptId)` 掩盖异参、拒绝或系统故障。已完成订单的可信回放不新增对Redis取号或号段预留可用性的依赖。

### 5.3 O2O 与 INSTORE

两个场景目前都在 Lifecycle 业务事务内生成 `SC_` 总单号，需增加场景应用层的事务外创建协调入口；Facade 委托它，不直接访问 Mapper。场景协调器与取号服务都禁止在外层实际事务中调用。

- O2O：把已有按渠道交易号的幂等准备/回放判断提取为短事务探测，保留现有“已启用用户绑定校验→已有交易探测→金额一致性校验”顺序；确需创建时预分配一个总订单号，再进入 `createPaymentPreparation` 的原子建单事务。当前 `replayExistingPayment` 校验金额，不比较完整请求指纹，本轮不趁编号改造增加或声称已有完整指纹比较。收银台调用继续在业务事务提交之后执行。
- INSTORE：按 `(channelCode, tradeId)` 探测已有流水，严格沿用已有作用域、金额和回放规则；已有结果直接回放。新创建路径预分配一个总订单号，进入 `createPaymentOrder` 后重新核查订单头与支付流水。若事务内发现可复用已有订单头，继续使用其已持久化总单号，未使用预分配号成为断号；不能因号码已分配绕过现有 1:1 流水约束。
- 并发预探测都未命中时允许分别取号，最后仍由业务永久键决定唯一订单；沿用/补齐对应场景的**已知业务键**竞争收敛，不能通过捕获所有 `DuplicateKeyException` 盲回放。
- 实际MySQL首创竞争键白名单：O2O为`uk_sc_o2o_detail_transaction`；INSTORE为`uk_sc_instore_flow_trade`、`uk_sc_instore_order_channel`及总单侧`uk_sc_order_legacy_key`（其生成列保护buyer_id/buyer_order_no，真实并发会先在总单插入处冲突）。只认可SQLState23000、错误码1062和完整键名，并在旧事务回滚结束后核同渠道trade及原有金额/project/profile/buyerUser规则；没有可信获胜流水则传播原冲突。编号唯一键及其它业务键不加入该白名单。
- 已有结果的探测必须复用原合同的权限与身份校验，不额外收紧或放宽。INSTORE现有流程先探测支付流水，回放核金额及订单头上的project/profile/buyerUser身份，未命中才进入用户和商户绑定校验；提取时保持这个顺序。取号失败后的只读竞争回放复用同一场景校验，不能只凭业务键返回订单。

所有业务事务仍完整覆盖总单、明细、资金、状态审计和 Outbox。前置取号不提前冻结资金、消费订单业务状态或调用远端。此次只重排编号分配，不改动商业准入判定、付款、履约或退款语义。

### 5.4 接口与代码边界

- 公共 HTTP/RPC 请求字段、签名版本、路径和返回字段保持原合同；`orderNo` 仍是稳定、不透明的字符串。
- 新增内部号码值对象和专用分配服务，不改变通用 `BusinessNoGenerator.next(prefix)`，不将新增数据库调用隐藏在其内部。
- CARD、O2O、INSTORE 所有总订单创建入口必须通过协调器进入；旧 Lifecycle 直接调用入口不能提供一个在事务内临时取号的兼容回退。
- `routing.domain` 不依赖 Spring/MyBatis；Facade 不依赖 DAL；供应链不访问 `system_*`/`member_*`。新的内部号码传递不穿过 Feign、不新增外部注册。
- 替换三个生产 SC 创建点和标准履约 BILL 创建点，并以架构/源码门禁防止新增生产订单入口绕过专用分配器。

## 7. 性能、连接预算与锁顺序

正常标准受理一次Lua消费两个号码，不执行MySQL取号事务或读取数据库时间。默认1000位置的专属段最多支持500批双号消费，首段/换段才更新数据库高水位；实际写入频率受场景混合、故障、重启与断号影响，不能把理想比例写成实测吞吐提升。

每实例只保留一个当前可用段及其floor，不预取多个段、不引入后台补段线程。Redis只保存段cursor，键在对应日期结束后7天清理；数据库预留记录永久保留。段失效、日期变化时丢弃本地当前段，历史状态不装入无界内存Map。

同一请求的预探测、号段预留/Redis消费、最终建单顺序运行，消费前释放准备阶段数据库连接；Redis调用不嵌在号段预留事务内，业务事务不访问发号Redis/流水表，不持有Redis消费互斥。现有业务事务和资格Reader所需连接预算继续适用。

Redis消费互斥等待、TIME及Lua命令都必须受请求剩余预算/取消约束；无预算的后台准备也使用有界等待和既有Redis命令超时。核对所用客户端对脚本的自动重试策略，禁止结果不确定后透明重试旧段；只有确认未执行的NOSCRIPT可重载。段切换只同步尝试一次，失败向外传播；跨日纠正最多重做一次，再次变化或不确定则失败，不循环追逐时钟。

MySQL号段事务继续走现有预算数据源，不通过裸池、自建连接或增大Hikari容量绕过守卫；Lua为常数步骤、最多两个号，不做KEYS扫描、无界循环或按全日订单遍历。实测验证数据库预留频次、Redis延迟、段浪费、互斥等待与故障行为，不宣称任意并发已达标。
