# 供应链管理端表单字典与标品标签设计

本文收回
`docs/superpowers/specs/2026-09-02-supply-chain-admin-frontend-api-design.md`
决策 **a6** 中「可售品类 / 商品类型 / 商品分类走类目树 id」的约定，改为三级独立封闭枚举（system 数据字典），并规定平台 SPU 打同一套标签、合作商品按三码整体命中供货配置。

金额口径、路径身份用业务 code、不按树拆账、L1/L2/L3 **结算价**语义不变。`sc_product_category` 与 `GET /supply-chain/categories` 仍给主数据/旧类目工具使用，**不再**给新增供应商供货配置、新增分销商、合作商品加购筛选做下拉或命中。

管理端 REST 风格仍以 09-02 为准。权限以
`docs/superpowers/specs/2026-09-03-supply-chain-admin-rbac-design.md`
为准。时间列遵循
`docs/superpowers/specs/2026-09-04-supply-chain-database-local-time-design.md`。
供应商表单已落地的六类字典见 09-02 §5.2.1，本文不重复迁移那六类。

本任务只交付后端枚举、Liquibase、REST 契约、测试与联调记录。**禁止修改任何前端工程**（含 `supplychainhubweb`），不建 `/scm` 适配层。前端读 `/system/dict-data/simple-list`、替换静态常量由独立任务实施。

## 1. 已确认决策

| 编号 | 决策 |
| --- | --- |
| d1 | 可售品类、商品类型、商品分类是**三套彼此独立**的封闭枚举，不校验父子链，不引用 `sc_product_category.id`。 |
| d2 | 供应商供货配置每一行三个码都必填；同一供应商三元组唯一。不得靠供货模式拆行。 |
| d3 | 平台 SPU 三个码都必填。合作商品新增、按 `supplierCode` 筛可加购 SKU：SPU 三码与某条供货配置**完全相等**则命中；0 条或多条 → `SUPPLIER_OFFER_OUT_OF_SCOPE`。 |
| d4 | 分销商档案只用前两级（多选标签）。**不**用档案品类限制分销商品加购。 |
| d5 | 三级词汇供应商与分销商共用（并集）。结算方式、对接方式复用已有 `supply_chain_settlement_method`、`supply_chain_integration_mode`。 |
| d6 | 分销商合作状态单独字典 `supply_chain_buyer_status`（文案「暂停分销」），不复用供应商「暂停供货」。 |
| d7 | 禁止字典编码与类目 id 双写；禁止把 `sc_product_category` 同步进字典。 |
| d8 | 不改已执行 changeset：供应链禁止回改 `001`–`023`；system 禁止回改 `001-supplier-form-dictionaries`。 |
| d9 | **不改前端。** 字典值用枚举名；前端 mock 小写码（`equity`、`direct`、`1/2/3`）不得写入 system 字典。 |
| d10 | 测试库已有供货配置 / 分销商范围 / SPU `primary_category_id` **不能**自动映射到枚举码。升级后清空或作废旧范围行；未打三码的 SPU 视为不可按供货配置加购，直到补齐。本轮管理端只在 `POST .../spus` 强制三码；**不提供** PATCH 补齐接口，历史行用 SQL 补齐或重建。 |

## 2. 三级封闭枚举

JSON 字段名（与 DDL COMMENT 同一中文）：

| JSON | 中文 | 字典类型 |
| --- | --- | --- |
| `sellableCategory` / `sellableCategories` | 可售品类（供应商配置单值；分销商档案多选；SPU 单值） | `supply_chain_sellable_category` |
| `productType` / `productTypes` | 商品类型 | `supply_chain_product_type` |
| `productClassification` | 商品分类（仅供货配置行与 SPU；分销商档案无此级） | `supply_chain_product_classification` |

同一编码允许出现在不同字典（例如 L1 与 L2 都有 `MOVIE`），靠 `dict_type` 区分。非法值 → `ENUM_NOT_OPEN`。管理员只改标签、排序、颜色，不得增改键值；供应链仍按封闭枚举拒绝未知码。

## 3. 分销商表单其它字典

与三级词汇一起由 system 新变更集写入。不按租户复制。

| 表单字段 | 字典类型 | 字典值（标签） | 控件 |
| --- | --- | --- | --- |
| 分销等级 | `supply_chain_distribution_level` | `1`（一级分销商）、`2`（二级分销商）、`3`（三级分销商） | 单选；提交仍为整数 `distributionLevel` |
| 合作模式 | `supply_chain_cooperation_mode` | `DIRECT`（直营分销）、`AGENT`（代理分销）、`CHANNEL`（渠道分销） | 多选 → `cooperationModes[]` |
| 分销商类型 | `supply_chain_distributor_type` | `ENTERPRISE`（企业）、`PERSONAL`（个人）、`PLATFORM`（平台入驻） | 单选 |
| 供货择优倾向 | `supply_chain_supply_preference` | `STABLE`（稳定优先）、`PRICE`（价格优先）、`COMPREHENSIVE`（综合优先） | 单选；不改变路由引擎 |
| 结算方式 | `supply_chain_settlement_method` | 已有，复用 | 单选 |
| 对接方式 | `supply_chain_integration_mode` | 已有，复用 | 多选 |
| 合作状态 | `supply_chain_buyer_status` | `ACTIVE`（正常）、`SUSPENDED`（暂停分销）、`BLACKLIST`（黑名单） | 单选；新增页不提供 `ARCHIVED` |
| 分销品类 | `supply_chain_sellable_category` | §2.1 | 多选 → `sellableCategories[]` |
| 商品类型 | `supply_chain_product_type` | §2.2 | 多选 → `productTypes[]` |

## 4. 供货配置与命中

### 4.1 REST

`GET/PUT /supply-chain/suppliers/{supplierCode}/supply-scopes`

每行：

| JSON | 必填 | 含义 |
| --- | --- | --- |
| `sellableCategory` | 是 | §2.1 |
| `productType` | 是 | §2.2 |
| `productClassification` | 是 | §2.3 |
| `supplyModes[]` | 是 | 既有五值 |
| `maxQuantity` / `minQuantity` | 是 | 与现规则相同 |

不再接受 `categoryL1Id` / `categoryL2Id` / `categoryL3Id`。

唯一键：`(supplier_id, sellable_category, product_type, product_classification)`。重复 → `SUPPLIER_SCOPE_CONFLICT`。不再调用 `CategoryChainValidator.requireActiveChain`。

改配置仍不改已发布 Offer；收窄只阻止新关联（命中改为三码比较）。

供应商列表筛选与聚合：`sellableCategories` / `productTypes` / `productClassifications` 为枚举名数组，不再是 `{id,name}`。

合作商品列表筛选同样改为三个可选枚举查询参数，不再用 `categoryL1Id` 等 Long。

### 4.2 平台 SPU

`sc_platform_spu` 新增三列（`VARCHAR`，封闭 CHECK），创建管理端标品时必填：

- `sellable_category` 可售品类
- `product_type` 商品类型
- `product_classification` 商品分类

`primary_category_id` 改为可空，**供货命中与按供应商筛 SKU 不再读取**。`GET /products/skus` 的类目过滤改为上述三码；带 `supplierCode` 时只保留三元组落在该供应商供货配置内、且尚无未退役 Offer 的 SKU。

主数据 `POST .../spus`：三码必填；`primaryCategoryCode` 可空、忽略其命中语义。本轮不提供更新 SPU 三码的 REST；历史未打码行用 SQL 补齐。`GET /supply-chain/categories` 与创建类目草稿接口保留，不删除。

合作商品列表展示三码本身；文案由前端字典翻译。不再用 `sc_product_category` 拼路径作为供货/加购主键。

分销商品/项目商品列表若仍展示「类目路径」，改为展示 SPU 三码（或前端译成标签），不要再 walk `primary_category_id` 祖先链作为加购条件。

### 4.3 分销商范围表

`sc_buyer_category_scope` 不再存类目主键。新变更集改为存编码：

- `scope_kind`：`SELLABLE`（品类） / `PRODUCT_TYPE`（类型）
- `scope_code`：对应枚举名
- 唯一键 `(buyer_id, scope_kind, scope_code)`（避免两级都出现 `MOVIE` 时撞 `(buyer_id, code)`）

请求/响应：`sellableCategories[]`、`productTypes[]`。列表筛选用 `sellableCategories`，不再用 `categoryL1Ids`。不再调用 `requireBuyerScopes`。

档案标签与是否允许关联某平台 SKU无关；加购规则仍只认平台 SKU 与项目目录既有约束。

### 5.2 供应链

## 6. 错误与日志

- 未知三级码、未知分销商表单枚举：`ENUM_NOT_OPEN`。
- 供货三元组重复：`SUPPLIER_SCOPE_CONFLICT`。
- 加购未命中或命中多于一行：`SUPPLIER_OFFER_OUT_OF_SCOPE`。
- `CATEGORY_CHAIN_INVALID` 不再用于供货配置或分销商档案；类目树主数据父子关系若仍校验，仅限 `GET/POST /categories` 自身。

入口日志打 `supplierCode`/`buyerCode`、三码、`offerNo`，不要刷全量枚举表。第三方/字典 HTTP 不在本切片调用：供应链**不**在请求线程调 system 字典接口做校验，只认本模块封闭枚举。

## 7. 测试门禁

`*Test`：

- 三枚举解析；未知码 `ENUM_NOT_OPEN`。
- 供货配置三元组唯一；不校验父子。
- Offer：三码全等命中一条；缺码 SPU 或无匹配配置 → `SUPPLIER_OFFER_OUT_OF_SCOPE`。
- 分销商范围两级独立多选；`MOVIE` 可同时出现在品类与类型而不唯一键冲突。
- 架构：供货命中与 SKU 供应商过滤不读 `ProductCategoryMapper` / `primaryCategoryId`。

`*IntegrationTest`：

- `024` 在已有库上 `EXECUTED` 一次；二次启动 `Run: 0`。
- 写入供货行与打标签 SPU 后，`POST .../offers` 命中；改 SPU 三码后新关联失败、已发布 Offer 不变。
- 分销商只存两级码，加购 SKU 不读档案范围表。

`*ContractTest`：供货配置与分销商档案 JSON 含三码字段名；不再要求 `categoryL1Id` 作为供货行主键；`GET/PUT …/invoice` 规则不变。

system：`002-admin-form-dictionaries` 结构测试与 MySQL 8.4 迁移测试（首次 `Run: 1`，再次 `Run: 0`），类型/值与本文一致。
