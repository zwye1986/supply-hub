# 管理后台售后批量操作设计

## 1. 背景与目标

管理后台当前只提供单笔同意售后、拒绝售后和确认退款接口。运营人员处理多张售后单时需要重复提交，
且无法在提交前统一确认整批数据是否仍满足状态机条件。

本次在 `AfterSaleController` 增加批量同意、批量拒绝和批量退款接口。批量接口必须复用单笔接口的
状态机、京东履约处理、支付退款路由、订单项状态维护和售后日志语义，不新增模块间 HTTP 自调用。

## 2. 接口契约

三个接口均使用 `PUT` 和 JSON 请求体，沿用对应单笔接口权限：

| 接口 | 请求体 | 权限 |
| --- | --- | --- |
| `/admin-api/trade/after-sale/batch-agree` | `{"ids":[1,2]}` | `trade:after-sale:agree` |
| `/admin-api/trade/after-sale/batch-disagree` | `{"ids":[1,2],"auditReason":"不符合售后条件"}` | `trade:after-sale:disagree` |
| `/admin-api/trade/after-sale/batch-refund` | `{"ids":[1,2]}` | `trade:after-sale:refund` |

`ids` 不能为空，元素不能为空，单次最多 100 张售后单；重复编号按首次出现顺序去重。批量拒绝的所有
售后单共用同一个非空审批备注。接口成功响应继续使用项目统一的 `CommonResult<Boolean>`，成功值为 `true`。

## 3. 状态机与处理流程

### 3.1 批量同意

1. 一次查询整批售后单，校验编号全部存在且状态均为 `APPLY`；
2. 仅退款售后进入 `WAIT_REFUND`，退货退款售后进入 `SELLER_AGREE`；
3. 每张售后单记录 `ADMIN_AGREE_APPLY` 日志。

### 3.2 批量拒绝

1. 一次查询整批售后单，校验编号全部存在且状态均为 `APPLY`；
2. 所有售后单进入 `SELLER_DISAGREE`，保存同一个 `auditReason`；
3. 每张售后单记录 `ADMIN_DISAGREE_APPLY` 日志；
4. 逐张恢复订单项的未申请售后状态，并重算京东履约快照或取消任务。

### 3.3 批量退款

1. 一次查询整批售后单，校验编号全部存在且状态均为 `WAIT_REFUND`；
2. 在首次退款调用前，逐张确认京东最终子订单已经满足退款条件；
3. 在首次退款调用前校验订单、平台积分退款快照及支付退款单号；同一主订单的多张非零退款不能在
   同一批次提交，避免触发支付服务“同一支付订单存在退款中记录”的确定性冲突；
4. 零元退款直接完成，非零退款复用既有普通支付或平台积分退款路由；
5. 每张售后单记录 `ADMIN_REFUND` 日志，非零退款仍由既有支付回调最终推进为 `COMPLETE`。

## 4. 原子性、并发与外部服务边界

批量方法使用同一个商城本地事务，采用“先全量校验、后逐条更新”的两阶段顺序。任一编号不存在、状态
不合法、京东退款条件不满足、并发条件更新失败或执行阶段抛出异常时，商城进程内的售后单、订单项、
履约快照和售后日志全部回滚，不返回部分成功结果。更新继续使用 `id + 原状态` 条件，防止并发审批覆盖。

`pay` 仍是外部服务，支付渠道已经受理的退款无法参与商城数据库事务，也无法物理撤销。因此批量退款的
“整体回滚”严格覆盖商城本地数据，并通过首次 RPC 前的全量本地校验降低部分外部受理概率；若后续某次
支付 RPC 失败，商城本地事务回滚，但此前已被支付服务或渠道受理的动作仍须依赖支付幂等、回调和人工
对账收敛。本次不把 `pay` 合并进商城进程，也不引入跨服务分布式事务。

## 5. 日志与可观测性

Controller 在三个批量入口记录管理员编号、去重前售后编号集合和批量数量；拒绝原因属于业务正文，不在
入口日志重复输出。Service 为每张售后单写入与单笔接口相同的操作类型、操作前后状态和管理员身份，确保
详情页日志语义一致。批量上限控制单次日志和外部调用规模，避免无界请求造成日志风暴。

## 6. 验证范围

验证批量请求参数、重复编号去重、混合售后方式同意、共用原因拒绝、零元与非零退款，以及任意编号不存在、
状态不合法、京东退款未就绪和并发状态变化时的整体回滚。人工联调步骤见
`docs/集成测试.md#6-管理后台售后批量操作联调`。
