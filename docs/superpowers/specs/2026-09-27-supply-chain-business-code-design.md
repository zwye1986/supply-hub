# 供应链中台业务编码规范化设计

日期：2026-09-27

## 1. 目标与范围

本设计统一七类新建业务对象的永久编码：平台 SPU、平台 SKU、商品分类、品牌、供应商、分销商（数据库模型名为 Buyer）和项目。只有 SKU→SPU、子分类→直接父分类、项目→分销商三种关系进入子对象编码。SPU 的品牌与主分类、供应商报价、分销商品、项目商品的归属不进入本轮编码。内部数据库主键和现有外部服务编码不变。

新规则只作用于上线后创建的对象。存量 `spu_code`、`sku_code`、`category_code`、`brand_code`、`supplier_code`、`buyer_code`、`project_code`、接口路径、订单快照和已发布事件均不改写。存量父对象可以继续新增子对象；为此只给旧 SPU、旧分销商和旧分类补内部短序号。所有编码一经创建永久不变，归档后不复用。

本设计覆盖所有能创建上述对象的后端入口，包括当前管理端接口与仍可写入的兼容接口。前端仓库 `/Users/mac/Documents/codeSpace/supplychainhubweb` 的管理表单需同步适配。

## 2. 编码结构与容量

字母前缀保持当前契约，数字部分使用 ASCII 十进制、三位左补零，范围 `001`～`999`；`000`、空格、小写字母、缺少下划线和多余段均非法。编号不含年份，不按时间重置。前缀与数字之间、父段与子段之间都用一个 `_` 分隔。

| 对象 | 新建编码格式 | 流水号作用域 | 手填 |
| --- | --- | --- | --- |
| SPU | `SPU_001` | 全平台 SPU | 允许 |
| SKU | `SKU_001_001` | 所属 SPU 内 | 允许 |
| 品牌 | `BRD_001` | 全平台品牌 | 允许 |
| 根分类 | `CAT_001` | 全平台根分类 | 允许 |
| 子分类 | `CAT_001_001` | 直接父分类内 | 允许 |
| 供应商 | `SPL_001` | 全平台供应商 | 仅系统生成 |
| 分销商 | `BYR_001` | 全平台分销商 | 仅系统生成 |
| 项目 | `PRJ_001_001` | 所属分销商内 | 仅系统生成 |

SKU 的父段是所属 SPU 的三位内部短序号；项目的父段是所属分销商的三位内部短序号。新建 SPU、分销商的内部短序号与其永久编码数字段一致，因此两个 SPU `SPU_001`、`SPU_002` 的首个 SKU 分别为 `SKU_001_001`、`SKU_002_001`。旧 SPU、旧分销商的内部短序号在迁移中分配，旧永久编码仍可为 ULID 或历史手填值。

分类支持无限级，因此子分类只记录**直接父分类**的内部全局短序号和本级在父分类中的流水号，不拼完整祖先路径。每个分类节点另有一个不可变、全局唯一的三位 `categoryNodeNo`，供其子分类引用；分类详情和管理树显式返回该字段并显示其含义。根分类的可见编码流水与 `categoryNodeNo` 分别分配：先有 `CAT_001`，再有其子分类 `CAT_001_001`，下一根分类仍可为 `CAT_002`。子分类的 `categoryNodeNo` 不一定能从它自己的永久编码推导；孙分类的父段取这个内部序号，实际父子关系仍以 `parent_id` 为准，不按字符串解析归属。

各根对象类型最多 999 个新格式号码；一个 SPU 最多 999 个新 SKU、一个分销商最多 999 个新项目、一个分类最多 999 个新子分类。分类节点内部短序号全局最多 999 个，故本期分类节点总容量为 999。任何作用域耗尽时拒绝新建，返回包含对象类型和作用域的明确容量提示；不自动扩位、不循环使用 `000`。容量包含已归档、已删除但曾成功分配的号码。

## 3. 手填与自动分配

SPU、SKU、品牌、分类在所有新建入口都可提交编码；不提交则系统分配。手填必须严格符合第 2 节格式。SKU、子分类的父段必须等于请求中真实父对象的内部短序号；服务端从已解析的父对象读取，不信任调用方另传父段。品牌与根分类仅校验本类型格式。供应商、分销商和项目始终由服务端分配，创建请求中的同名编码字段若存在，应明确拒绝而非静默采用。

手填 `100` 时，只要该类型或父级作用域中 `100` 未被占用，即可先分配；自动创建随后优先取 `001`～`999` 中**最小未用号码**，逐步填补较小空位。因此在手填大号之后，号码可暂时不连续。并发竞争、事务回滚及归档不会导致重号；成功分配过的号码永不回收。创建事务失败时占号一同回滚，号码仍可使用。

旧 SPU、旧分销商的内部短序号与新对象的可见根号共享各自的父段号码池。若旧 SPU 已占内部短序号 `100`，即使系统里没有永久编码 `SPU_100`，新建 SPU 也不得手填 `SPU_100`；返回“父段 100 已被旧 SPU 占用”的具体提示。分销商同理。分类根号与分类节点内部号为两套号码池，不受该规则影响。业务表原有全局唯一索引继续保留，任何与存量永久编码直接重名的输入也必须拒绝。

## 4. 归属与不可变性

编码反映创建时已确认的三种父子关系，数据库关联字段仍是归属事实来源。SKU 不得移至另一 SPU；分类创建后不得改挂到另一父分类或根；项目创建后不得变更分销商，草稿态也不例外。编辑接口若显式提交不同归属，返回稳定业务错误；缺省归属字段可保持原值。分类更新请求原有 `parentCategoryCode` 三态改挂语义终止，前后端必须同时收口。项目更新接口原有“草稿态可换分销商”例外终止。分类名称、状态、排序等非归属字段仍可更新；SPU 的品牌和主分类仍按既有业务规则更新，其变化不影响 SPU/SKU 编码。

归属不可变规则也作用于旧编码对象，避免新旧对象在同一编辑入口产生不同语义。对存量分类和项目的历史归属不追溯调整。

## 5. 存储、迁移与并发

供应链独立库增加编号作用域、号码占用记录以及三类父对象的内部短序号；新增表名使用 `sc_` 前缀，表间仍无物理外键。号码占用唯一键至少覆盖 `(编码类型, 父级作用域, 数字序号)`；业务表永久编码唯一键继续作为第二道防线。根对象使用固定根作用域；子对象作用域使用父对象内部 ID，不用前端传入的字符串。分类节点内部短序号使用独立全局作用域，根分类可见流水使用另一作用域。内部短序号持久化并有唯一约束，不能靠业务编码事后截取推导。七类对象统一调用新的编号分配服务；既有 `BusinessNoGenerator` 继续服务其它未纳入本轮的业务编号，不改变其公共行为。

创建时在 `supplyChainTransactionManager` 事务内先锁定作用域行，再校验、占号并插入业务对象；组合创建 SPU+SKU 在同一事务分配父号和子号。自动分配从该作用域的已占号码中寻找最小未用号；手填在相同锁下验证格式、父段和可用性。分类创建需要同时取得内部节点号和可见号码，锁顺序固定为“分类内部全局作用域→根或父分类可见作用域”，避免互相等待。所有实例都共享 MySQL 行锁与唯一约束，不以进程内锁保证正确性。

部署迁移按稳定 ID 顺序给所有旧 SPU、旧分销商和旧分类节点补内部短序号，包含归档对象。已有永久编码恰好符合新根格式且号码无冲突时，旧 SPU、旧分销商优先占用其可见数字；其余旧对象取剩余最小号。已有分类编码与新格式直接重名时，自动分配必须跳过该永久编码。迁移前在作用域锁内一次解析历史编码并预检：父对象总数、已分配内部号的重复、符合新格式的可见号码重复、可见号码与其他对象已有内部号或占号记录冲突，以及剩余号码是否足够；分类节点也核对已有内部号、占号记录与剩余容量。冲突报告包含表名、对象 ID、永久编码及号码；异常时阻止上线，不截断数字、不自动改写旧编码。旧编码不符合新格式是正常数据分支，解析时不靠捕获格式异常判断。迁移可重入，已分配内部短序号保持不变。

分配时只检查目标业务表中可能与本次候选号码相同的永久编码。手填仅按完整编码查一次；自动分配从本作用域未占的 `001`～`999` 构造至多 999 个候选，用业务表永久编码唯一索引做有界匹配，内存中仅保留命中的编码。分类根与子分类共用分类业务表，但按各自完整编码匹配。数据库唯一键仍防护其它写入路径在检查与插入之间的竞争。永久编码重名、旧 SPU/分销商父段占用、普通作用域占号按此顺序判别，并使用不同错误码；旧父段须能对应具体旧对象，不把已删除业务行留下的占号误称为旧对象。

Redis/Redisson 可作为未来有锁竞争证据时的性能优化，不作为本期编号正确性前提。Redis 锁无法与 MySQL 事务原子提交，租约过期后仍需数据库行锁和唯一约束防重。供应链进程不为本功能新增 Redis 强依赖；多实例并发、数据库锁等待超时和唯一键冲突均需明确错误或受控重试，不得吞异常。

编号分配入口显式传递操作人 ID；没有人工操作人的系统调用记为系统操作，入口与成功结果的字段包括对象类型、作用域、手填/自动、分配结果、耗时和操作人。高频成功路径使用 debug；冲突业务错误在供应链 HTTP 边界按错误码计数并采样告警，保持每次请求的错误响应不变，避免全局业务异常处理器再逐次打印同一冲突。日志不记录供应商/分销商联系人等敏感资料。改动仅落在独立的 `SupplyChainServerApplication` 数据源和事务内，需运行供应链架构测试并确认其它七个独立进程不依赖新编号表或本进程事务。

## 6. 接口、前端与错误提示

保持现有创建、详情、列表 URL 和永久编码字段名。创建响应仍返回永久编码；SPU 详情增加只读 `codeScopeNo`，供编辑时新增 SKU 展示真实父段；分类详情和管理树增加只读 `categoryNodeNo`，字段说明为“分类节点内部全局短序号，供直接子分类编号引用”。手填编码的后端校验覆盖管理端和兼容入口，不依赖前端正则作为唯一防线。

错误按“格式错误、父段不匹配、永久编码已存在、父段已被旧对象占用、作用域号码已占用、容量已满、归属不可变”分类，并给出具体中文提示。例如：`SKU 编码应为 SKU_001_001；当前 SPU 的父段为 001，子段须为 001–999`；`分类编码 CAT_002_005 的父段 002 与所选父分类的内部短序号 003 不一致`。格式解析直接返回结构化错误类别，不根据中文文案反推；父段不匹配提示同时包含用户输入和真实父段。旧父段占用提示明确写旧 SPU 或旧分销商。项目归属不可变提示对草稿和非草稿使用同一语义。手填大号合法时不以“非下一个号码”为由拒绝。接口错误码在实现阶段从供应链错误码段分配，不复用语义不同的旧错误。供应商、分销商和项目管理端创建请求只要出现同名编码字段（包括 `null` 或空字符串）就返回禁止手填错误；编辑请求的路径编码仍作为身份，现有不带编码的编辑载荷不受影响。

管理端新建 SPU/SKU 输入框允许手填并标注“不填自动生成”、当前父段和 3 位格式；编辑时编码只读。品牌与分类表单更新格式提示；分类选择父级后展示该父级 `categoryNodeNo` 和可填写的编码前缀。分类编辑禁用父级选择，项目编辑禁用分销商选择；后端仍校验不可变性。供应商、分销商、项目编号保持系统生成的只读展示。前端只做友好提示，不自行推断最终可用序号；并发占号冲突以服务端响应为准。

## 7. 测试与联调门禁

- `*Test`：七类格式、父段匹配、最小未用号、手填大号、边界 `001`/`999`、容量耗尽、错误映射和归属不可变。
- `*IntegrationTest`（`supply-chain-integration`）：真实 MySQL、Liquibase、编号占用与业务创建同事务；两个服务实例并发自动创建、并发手填同号、回滚重用、归档不复用、旧父对象补号、旧格式碰撞、分类双作用域锁顺序与容量阻断。
- `*ContractTest`：管理端与兼容写入口的相同校验及中文提示；分类详情/管理树新增字段；分类和项目改归属被拒绝；旧编码 URL 与订单快照继续可读。
- `*ArchitectureTest`：运行 `SupplyChainModuleArchitectureTest`，确认编号服务不跨供应链库、不破坏应用层与 Facade 边界，新增管理端 HTTP 映射若存在仍有 `@PreAuthorize`。
- 联调场景、前置数据、接口请求、页面检查和排障步骤持续写入 `docs/集成测试.md`；管理前端执行类型检查/构建并用实际后端验证手填、自动生成和失败提示。

## 8. 发布顺序与回退

先上线数据库变更与旧父对象内部短序号补号，核对容量、唯一性及可重入性；再上线后端统一分配与校验；最后上线管理前端提示和归属锁定。后端上线前不得让前端发送新格式手填码。灰度期间旧编码继续读取，新创建对象一律使用新规则，不按调用方版本切换。若新编号链路故障，停止新建并回滚应用版本；已经成功分配的编号仍保留，不回填旧格式、不重编号。回退不会改写历史订单或事件。

本设计覆盖既有设计中的编码生成与归属编辑决策：`2026-09-11-supply-chain-product-center-design.md` 的 d5/d11/分类更新，以及 `2026-09-02-supply-chain-admin-frontend-api-design.md` 的项目草稿换分销商行为。原有其它商品、项目状态和目录规则保持有效。
