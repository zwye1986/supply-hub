# 供应链管理端开票信息设计

本文取代 08-28 `g13` 与 09-02 `a2`/`a11` 中「开票本期不做」的约定，为供应商、分销商详情「开票信息」页签提供查询与保存。金额口径、路径身份用业务 code、不按树拆账等其余内核不变。

管理端 REST 风格仍以
`docs/superpowers/specs/2026-09-02-supply-chain-admin-frontend-api-design.md`
为准。权限标识以
`docs/superpowers/specs/2026-09-03-supply-chain-admin-rbac-design.md`
为准。时间列遵循
`docs/superpowers/specs/2026-09-04-supply-chain-database-local-time-design.md`。

本任务只交付后端表、REST、测试与联调记录。**禁止修改任何前端工程**（含 `supplychainhubweb`），不建 `/scm` 适配层，不为迁就现有 `/scm/supplier/invoice/get|save` 再做兼容路径。页签在关 mock 前仍走前端本地 mock，与本后端互不影响。

## 1. 已确认决策

| 编号 | 决策 |
| --- | --- |
| i1 | 供应商与分销商都做，字段与校验同一套。 |
| i2 | 独立 1:1 开票表；不是档案主表上的一组列。 |
| i3 | GET 无开票行时用档案预填返回，**不 insert**。 |
| i4 | PUT upsert 只写开票表，**不回写**档案同名字段。 |
| i5 | 路径挂在现有资源下：`GET/PUT …/suppliers/{supplierCode}/invoice`、`GET/PUT …/buyers/{buyerCode}/invoice`。禁止 `/get`、`/save`、`/scm`。 |
| i6 | 抬头类型 JSON 为 `ENTERPRISE` / `PERSONAL`，配置到 system 数据字典 `supply_chain_invoice_title_type`（名称“开票抬头类型”）。前端现有 `1/2` 由前端映射。 |
| i7 | 开票是详情子资源：GET 走对应 `query`，PUT 走对应 `update`；不单开权限、不改 `system_menu`。 |
| i8 | 供应商/分销商详情 JSON **不含**开票块；只走独立子资源。 |
| i9 | **不改前端。** 不改 `supplychainhubweb` 或其它前端仓库的任何文件；不关 mock；不把现页签接到本接口。 |
| i10 | 开票表全部明文落库（含开户账号、电话、信用代码）。不信封加密、不建 cipher/key_version 列。档案主表的开户账号加密策略不变。 |

## 2. 路径

网关前缀 `/admin-api`。身份在路径上，不用 `?supplierId=`。

| HTTP | 路径 | 权限 |
| --- | --- | --- |
| GET | `/supply-chain/suppliers/{supplierCode}/invoice` | `supply-chain:admin` 或 `supply-chain:supplier:query` |
| PUT | `/supply-chain/suppliers/{supplierCode}/invoice` | `supply-chain:admin` 或 `supply-chain:supplier:update` |
| GET | `/supply-chain/buyers/{buyerCode}/invoice` | `supply-chain:admin` 或 `supply-chain:buyer:query` |
| PUT | `/supply-chain/buyers/{buyerCode}/invoice` | `supply-chain:admin` 或 `supply-chain:buyer:update` |

主体不存在：`SUPPLIER_NOT_FOUND` / `BUYER_PROFILE_NOT_FOUND`。没有开票行不 404。

挂在现有 `SupplierAdminController` / `BuyerAdminController`，`@Tag` 沿用类上已有名称；每个方法有 `@Operation`。

## 3. 响应与请求体

供应商、分销商同一套字段（主体 code 字段名不同）。VO `@Schema` 与 DDL `COMMENT` 使用同一中文表述。

| JSON | 含义 |
| --- | --- |
| `id` | 开票行内部主键；未保存为 `null` |
| `persisted` | 是否已有开票行 |
| `supplierCode` / `buyerCode` | 路径上的业务编码 |
| `titleType` | `ENTERPRISE` 企业 / `PERSONAL` 个人（字典 `supply_chain_invoice_title_type`） |
| `invoiceTitle` | 开票抬头 |
| `socialCreditCode` | 统一社会信用代码 |
| `phone` | 电话 |
| `bankName` | 开户行 |
| `bankAccount` | 开户账号（明文读写） |
| `invoiceAddress` | 开票地址 |
| `createdAt` / `updatedAt` | 仅已保存行有值，Asia/Shanghai |

PUT 只读 body 中的开票字段；忽略客户端 `id`、`persisted`、主体 code。路径 code 为准。

### 3.1 抬头类型数据字典 `supply_chain_invoice_title_type`

供应商与分销商详情的开票信息页签共用抬头类型数据字典：

| 字典类型 | 字典名称 | 备注 |
| --- | --- | --- |
| `supply_chain_invoice_title_type` | 开票抬头类型 | 供应商与分销商开票信息共用；提交值为titleType枚举名（ENTERPRISE企业/PERSONAL个人） |

字典项数据：

| 编码 / value | 标签 / label | 排序 | 颜色类型 | 备注 |
| --- | --- | --- | --- | --- |
| `ENTERPRISE` | 企业 | 1 | `primary` | 企业抬头 |
| `PERSONAL` | 个人 | 2 | `info` | 个人抬头 |

前端通过 `/admin-api/system/dict-data/simple-list` 读取该字典渲染下拉或标签；后端继续使用 `InvoiceTitleType` 封闭枚举进行强类型校验与逻辑处理。

## 4. GET

1. 主体存在且已有开票行：原样返回库内明文，`persisted=true`。
2. 主体存在且无开票行：按 §5 预填，**不写库**，`persisted=false`，`id`/`createdAt`/`updatedAt` 为 `null`。
3. 预填允许信用代码、开户行、账号、地址、电话为空；空不挡查询。

档案日后修改：已保存的开票行保持原值；未保存时下次 GET 用当时档案重新预填。

## 5. 预填映射

`titleType` 默认 `ENTERPRISE`。

| 开票字段 | 供应商来源 | 分销商来源 |
| --- | --- | --- |
| `invoiceTitle` | `legalEntityName`，空则 `supplierName` | `legalEntityName`，空则 `buyerName` |
| `socialCreditCode` | `creditCode` | `creditCode` |
| `phone` | 主联系人手机（`sort_no` 最小的联系人） | 主联系人手机（`sort_no` 最小的联系人；没有联系人行则 `sc_buyer.contact_mobile`） |
| `bankName` | 档案 `bankName` | 档案 `bankName` |
| `bankAccount` | 档案开户账号解密后的明文（只用于预填；写入开票表后不再加密） | 档案开户账号解密后的明文（只用于预填；写入开票表后不再加密） |
| `invoiceAddress` | `contactAddress` | `contactAddress` |

不用法人手机号预填电话。

## 6. PUT

对主体行 `SELECT … FOR UPDATE`，再按 `supplier_id` / `buyer_id` upsert。后写覆盖。`created_by` / `updated_by` 为当前管理端用户 id。时间取 `SupplyChainDatabaseClock`。

不回写档案。不校验开票信用代码与档案 `creditCode` 是否相同。开票信用代码不做跨主体唯一。

### 6.1 校验

未知 `titleType` → 已有 `ENUM_NOT_OPEN`。

两种类型都必填：`invoiceTitle`、`phone`。缺一 → `INVOICE_FIELD_INVALID`（`1_050_001_076`，文案「开票信息字段不完整或与抬头类型冲突」）。

企业再必填：`socialCreditCode`、`bankName`、`bankAccount`。缺一同上。

个人：后端将 `socialCreditCode`、`bankName`、`bankAccount` 置空后落库，即使请求带了这些字段。

`invoiceAddress` 可空。空白字符串存 `null`。

## 7. 表

Liquibase 只追加 `023-admin-invoice`（`023-admin-invoice.sql`），禁止回改 `001`–`022`。新表时间列注释写 Asia/Shanghai。逻辑引用主体 id，不建物理外键。

`sc_supplier_invoice`：

| 列 | 类型 | COMMENT |
| --- | --- | --- |
| `id` | BIGINT PK | 供应商开票信息内部主键 |
| `supplier_id` | BIGINT UK | 供应商内部主键，逻辑引用sc_supplier.id |
| `title_type` | VARCHAR(16) NOT NULL | 抬头类型：ENTERPRISE企业，PERSONAL个人 |
| `invoice_title` | VARCHAR(256) NOT NULL | 开票抬头 |
| `social_credit_code` | VARCHAR(32) NULL | 统一社会信用代码 |
| `phone` | VARCHAR(32) NOT NULL | 电话 |
| `bank_name` | VARCHAR(128) NULL | 开户行 |
| `bank_account` | VARCHAR(64) NULL | 开户账号 |
| `invoice_address` | VARCHAR(512) NULL | 开票地址 |
| `version` | BIGINT | 乐观锁版本号 |
| `created_by` / `updated_by` | BIGINT | 创建人用户ID / 最后修改人用户ID |
| `created_at` / `updated_at` | DATETIME(3) | 创建时间，Asia/Shanghai / 最后修改时间，Asia/Shanghai |

CHECK：`title_type IN ('ENTERPRISE','PERSONAL')`。表 COMMENT：`供应商开票信息`。

`sc_buyer_invoice` 对称，`buyer_id` 逻辑引用 `sc_buyer.id`，表 COMMENT：`分销商开票信息`。

## 8. 存储与日志

开票行不加密：`bank_account`、`phone`、`social_credit_code` 均为明文列。禁止把档案信封加密套到开票表。预填时可以从档案密文解密一次，写入开票表的是明文。

日志不得打印完整开户账号、电话、统一社会信用代码。入口日志只记主体 code、`titleType`、`persisted`。

## 10. 测试门禁

`*Test`：预填映射（公司名称优先、无联系人电话为空）；个人保存清空银行字段；缺必填与非法枚举；`InvoiceTitleTypeDictionaryLiquibaseTest` 校验变更集文件语法、注册、封闭枚举值、幂等防破坏。

`*IntegrationTest`：`023` 建表；PUT 后改档案 GET 仍为开票行；`bank_account` 明文落库且 GET 原样返回；不回写档案 `bank_name`/`credit_code`/联系人手机；无行 GET 不产生 insert。

`*ContractTest`：上述四条映射存在且有 `@Operation`；路径不含 `get`/`save`/`create`/`page`；`titleType` 为英文枚举。删除「Controller 不得包含 invoice」断言。类目/标品/项目契约继续禁止**自己的**路径出现 invoice，不要误伤供应商/分销商。

`*ArchitectureTest`：开票应用服务不访问供应商 Adapter。
