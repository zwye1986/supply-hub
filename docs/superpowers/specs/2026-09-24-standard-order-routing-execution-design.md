# 标准商品订单路由执行对齐设计（2026-09-24）

## 1. 目标与边界

本设计修订 `2026-09-23-order-frontend-alignment-and-routing-prd-model-design.md` 的 §5.3、§5.4：以最新 PRD §8.13.4.2 的运行时语义为准，实现标准商品订单的逐级规则匹配、候选资格筛选与每日累计供货配额。管理端前端实现进度不构成本次后端门禁。供应链仍只读写独立 `sc_*` 表；供应商和订单数据均属于供应链库。

## 2. 已确认业务决策

1. 规则按以下固定层级逐级匹配：四维组合 → 分销商+项目+商品类型 → 分销商+商品类型 → 项目+商品类型 → 商品类型 → 分销商+项目通用（全部商品类型、全部供应商）→ 全局默认。同层再按 `rule_priority` 与 `rule_code` 稳定裁决，不再按指定维度数量打分。新增分销商+项目+商品类型专属层排在四维组合之后、粗粒度分销商/项目层之前，使最具体的业务配置优先；分销商+项目通用层排在所有商品类型专属层之后，使已有按类型配置的结果保持优先。
2. 四维组合的供应商维度取规则中指定的供应商候选；订单输入不预设供应商。候选仍须通过供应商状态、有效 Offer、数量范围及动态事实校验。
3. 不属于上述七级的范围组合在保存和策略发布时拒绝，防止形成永远无法命中的规则；管理端返回明确的范围组合业务错误，而非通用 500。受保护的全局默认规则保持四个维度均为 `ALL`。
4. “供货上限”指每供应商+平台 SKU 的自然日累计配额，区别于 Offer 版本的单笔 `max_quantity`。路由选中时须在订单受理事务内原子占用；失败或取消后释放。自然日按供应链数据库的 `Asia/Shanghai` 本地时间划分。
5. 配送区域筛选仅在订单携带收货地区时适用。当前标准商品受理无收货地区，不以供应商区域配置拒绝虚拟商品订单。
6. 命中停用规则时跳过该规则，继续匹配同层其它启用规则及下一层；全局默认也仅在启用时兜底。
7. PRD 未指定排序截断的 `N₁`、`N₂` 值和配置来源。本次沿用现有确定性三级比较，待值明确后再增加截断。

## 3. 规则匹配

每条规则的范围模式必须属于以下七类：

| 层级 | 级别名称 | 分销商 | 项目 | 商品类型 | 供应商 | 说明 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 四维全指定 | SPECIFIED | SPECIFIED | SPECIFIED | SPECIFIED | 人工限定供应商候选池 |
| 2 | 分销商+项目+商品类型 | SPECIFIED | SPECIFIED | SPECIFIED | ALL | 细粒度项目专属品类自动比价 |
| 3 | 分销商+商品类型 | SPECIFIED | ALL | SPECIFIED | ALL | 分销商品类规则 |
| 4 | 项目+商品类型 | ALL | SPECIFIED | SPECIFIED | ALL | 跨分销商项目品类规则 |
| 5 | 商品类型 | ALL | ALL | SPECIFIED | ALL | 全平台品类规则 |
| 6 | 分销商+项目通用 | SPECIFIED | SPECIFIED | ALL | ALL | 项目全品类兜底规则 |
| 7 | 全局默认 | ALL | ALL | ALL | ALL | 全平台兜底 |

前三个输入判定键沿用现有实现：分销商编码从 `sc_buyer` 解析，项目编码从 `sc_buyer_project` 解析，商品类型编码从平台 SKU 对应 SPU 解析。`SPECIFIED` 必须包含对应输入编码；供应商 `SPECIFIED` 表示规则候选池已显式限定，不对订单输入做供应商相等判断。分销商+项目+商品类型层与分销商+项目通用层均要求订单的分销商和项目分别命中规则范围；其 `AUTO + supplierMode=ALL` 候选仍按当前 SKU 的有效报价动态解析。先在启用规则中确定最高命中层，再在该层使用 `rule_priority`、`rule_code` 稳定裁决。停用规则跳过；没有启用规则命中且默认规则停用时拒绝路由。

管理端保存校验与底层策略发布校验共用同一范围模式分类函数，避免管理端允许而发布器拒绝，或直调发布器绕过校验。分销商与项目都为 `SPECIFIED` 时（第 1、2、6 级），每个项目必须归属于至少一个所选分销商；否则保存及直接发布都拒绝，避免不可命中的范围。草稿创建时校验一次，发布时还须按库中范围明细重新校验，防止历史草稿或创建后变化的关联进入生效版本。一个分销商没有被任何所选项目覆盖时，该编码不会单独扩大项目范围。管理端对不支持的组合返回 `ROUTING_RULE_SCOPE_UNSUPPORTED`，对项目归属不匹配返回 `ROUTING_RULE_PROJECT_BUYER_MISMATCH`，两者均为 `DO_NOT_RETRY`。前端保存前提示范围模式问题；项目归属由后端校验并返回业务错误。历史版本中的非七级规则保留审计数据，但运行时不应悄然赋予未定义层级；部署迁移前须检查是否存在此类生效规则。

本次只增应用层分类与校验，不改 `sc_std_routing_rule` 或范围明细 DDL。新版本一旦发布，旧版本程序不认识第七级，回滚应用前须先将当前生效策略发布回只含旧五级/六级的版本；发布和消费运行同一供应链进程，避免新旧程序并行读取新规则。

## 4. 每日累计配额与并发

配置归属为 `(supplier_id, platform_sku_id)`，不得复用 Offer `max_quantity`：同一供应商可对一个平台 SKU 建立多个 Offer，而累计配额须对这些 Offer 共用。新增 `sc_supplier_sku_daily_quota`，以独立 `id` 为主键、`(supplier_id, platform_sku_id)` 为唯一业务键，保存正整数 `daily_limit`、乐观锁版本和本地创建/更新时间；无配置行表示不设累计配额，兼容现有供应商。管理端在 `/supply-chain/supplier-config/daily-quotas` 提供按供应商编码+平台 SKU 编码读取与设置接口，设置值为正整数，删除配置则恢复无限额；接口只管理配置，不允许直接改已占用数量。每个 HTTP 映射均带 `@PreAuthorize`。

标准商品受理当前已在同一供应链事务中先按固定顺序锁定 Listing 和平台 SKU，随后执行路由并插入订单；管理端设置或删除配额时也先锁该平台 SKU，使配置变更与受理顺序一致。配额检查使用该 SKU 锁串行化同 SKU 的并发受理：读取当日该供应商、SKU 已占用的订单数量，加本次数量不得超过限额；路由选中后在**同一事务、释放 SKU 锁之前**插入带所选供应商的订单。事务回滚则不占用。已进入订单但最终状态为失败或取消的订单不计入占用；成功履约的订单继续计入当日用量。独立调用路由服务的诊断/测试查询不创建订单，不能视为配额占用；生产受理路径必须保持锁、检查、插单在同一事务内。

查询采用订单事实而非可漂移的内存计数。需要为 `(platform_sku_id, display_supplier_id, created_at)` 增加索引，并在真实 MySQL 集成测试中验证临界值与并发。`created_at` 的日窗口由供应链数据库本地时钟计算，区间采用 `[当日 00:00, 次日 00:00)`。如果未来实现供应商失败后的重路由，必须在同一事务中更新当前占用归属并重新校验新供应商配额；当前代码尚无重路由入口。

## 5. 配送区域

`RoutingInput` 可携带可空的六位收货行政区划编码。编码为空时跳过区域筛选；非空时 `NATIONWIDE` 可通过，`DESIGNATED` 读取 `sc_supplier_delivery_region` 配置。配置编码等于收货编码，或为收货节点在 `AreaUtils` 行政区划树中的任一祖先时，视为覆盖；未知编码仅允许字符串全等，不用前缀猜测父子关系。其它/缺失的供应商配送区域模式在有收货地区时失败关闭。当前 CARD 虚拟商品受理没有该输入，保持为空。

## 6. 三策略排序

保留 `SupplierRoutingEngine` 现有 `STABLE`、`PRICE`、`COMPOSITE` 的三级字典序比较及确定性同分裁决。候选资格先过滤，再比较三个策略；`N₁`、`N₂` 的截断逻辑在产品给出数值与配置来源后另行设计，不以猜测的默认值改变选路结果。

## 7. 测试与联调门禁

- 纯逻辑单测：六级范围分类、非法组合业务错误、第六级与类型专属层优先级、停用回落、同层裁决、排序边界。
- 真实 MySQL 集成测试：分销商+项目规则发布、项目归属校验、AUTO+ALL 候选与命中顺序、供应商候选过滤、每日配额临界值与并发受理、失败/取消释放、跨自然日重置。
- 架构测试：`routing.domain` 保持无 Spring/MyBatis 依赖；管理端新增映射须有 `@PreAuthorize`；供应链不得访问其它模块数据表。
