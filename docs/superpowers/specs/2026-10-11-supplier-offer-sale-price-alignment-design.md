# 供应商合作商品销售建议价口径修复

> 2026-10-11。用户已授权“细化修改方案，审查后执行代码修复”。本设计先完成独立审查，再实施并复审；实现与测试结果写入 `docs/集成测试.md`，不把本地修复作为部署验收。

## 1. 问题与目标

SPU_011 / SKU_011_001 的 SKU 销售建议价为9600分、固定供应价9500分，新通用定价版本2为READY，旧L1身份与版本均缺失。合作列表却将旧L1字段 `suggestPriceCents` 显示为销售建议价，因此为空。新增选品用市场价代填建议价、改价用旧L1回填、DISCOUNT服务校验用客户端提示价而有效供货价计算用SKU主数据，形成读写计算口径不一致。

目标：合作列表正确显示96.00元；在旧L1为空或不同、市场价与销售建议价不同的情况下，新增、改价及商业条款折扣试算统一使用SKU销售建议价。客户端提示值不再决定服务准入。

## 2. 方案比较与决策

1. 推荐：新增 `suggestedSalePriceCents`，保留 `suggestPriceCents` 的旧L1原义，前端显式读取新字段，服务端验证权威SKU价格。增量JSON兼容，无DDL/迁移，新旧价格语义独立。
2. 直接将旧字段改为销售建议价：改动较少，但静默改变已公开的B端结算字段语义，拒绝。
3. 前端逐行补查商品详情或补写L1：引入重复请求或污染结算主数据，不解决后端折扣校验不一致，拒绝。

## 3. 后端响应与兼容契约

`GET /admin-api/supply-chain/suppliers/{supplierCode}/offers` 的 `OfferListItem` 新增 `Long suggestedSalePriceCents`，取已加载的 `PlatformSkuDO.suggestedSalePrice`，不额外查询，不取市场价、面值、L1、通用默认分销价或最终销售价。字段注释与DDL COMMENT一致：`建议零售价/销售建议价，单位为分`。SKU缺失或销售建议价缺失返回null；0为有效展示值。

旧 `suggestPriceCents` 仍按旧L1身份/当前版本读取；保留JSON字段、原义和空值行为。`unitPriceCents` 继续表示身份行固定供应价；不修改履约版本冻结价、状态、评分、报价版本或数量。

## 4. 服务端折扣准入

`resolveLine` 已加载并校验所属SPU与SKU为ACTIVE；价格校验改为接收该SKU的 `suggestedSalePrice`。DISCOUNT要求该权威值非空且>0、`discountBp`仍在1..10000。请求 `suggestedPriceCents` 保留为历史兼容字段，可以缺省，可以与SKU值不同，服务端不使用它作为价格来源，也不校验它与SKU值相等，避免旧调用方被非权威字段锁死。

新增稳定业务码 `SUPPLIER_OFFER_SUGGESTED_SALE_PRICE_INVALID` = `1_050_001_178`，文案“折扣模式要求SKU销售建议价大于0，请先在商品中心配置”，重试映射 `DO_NOT_RETRY`，用于权威SKU价缺失/0/负数。通过ServiceException交给现有HTTP终结边界单行WARN；本服务不记录异常堆栈，不修改共享异常处理。非法折扣范围仍保持现有错误处理，本次不扩展其语义。FIXED/REALTIME校验保持原样。

在创建与改价两条路径均执行同一校验。读取价格使用现有事务内SKU快照，本次不调整锁顺序、事务隔离、并发协议或启动/RPC/缓存配置。发生SKU后续改价，继续沿既有PricingDependencyChangedEvent重算；已有有效履约版本冻结价保持。

## 5. 前端展示与写入

前端全部改动限定 `/Users/mac/codespace/supplychainhubweb`。

1. API `OfferListItem` 新增可空 `suggestedSalePriceCents`。销售建议价列与改价回填只用该字段，严禁回退旧L1/市场价/供应价。0显示0.00，null/字段缺失显示“-”。历史 `suggestedPriceCents` 请求字段注明只读提示价、非服务端权威基数。
2. 新增选品 `flattenProductPage` 保留 `sku.suggestedSalePrice`，选中时用该值填请求兼容提示字段，不再用 `sku.marketPrice`。市场价列保持市场价。批量模式切换时不覆盖SKU建议价。
3. `formatSupplyPrice` 的DISCOUNT商业条款试算使用新字段 × discountBp / 10000，正数建议价是折扣候选前提；缺失/0则显示“-”，FIXED仍展示unitPriceCents，REALTIME仍“-”。保持CNY分HALF_UP，前端与后端在合法范围一致。
4. 新增和改价在DISCOUNT且销售建议价缺失/非正时给出明确中文提示并阻止无效请求；FIXED商品即使销售建议价为0或缺失仍可按既有规则提交。服务端仍负责最终准入，页面加载后价格变化不能靠前端防护保证。
5. 供应价列继续表示当前身份行商业条款的价格/试算，不改为有效履约版本价；在列头说明“按当前商业条款展示；已发布履约版本按冻结价执行”。这是对现有投影的准确说明，不新增版本价字段。

新字段缺失时不从相似名称字段兜底；发布顺序后端先于前端，单独只发后端时旧前端仍会空显，必须配套发布后才算完成页面修复。

## 6. 范围与架构

新增字段与校验均在现有 `tradecore.supply.application`；不跨库、不新增RPC、不调整Mapper SQL或模块依赖方向。修改前已读取SupplyChainModuleArchitectureTest与全系统日志规范。

当前供应商履约发布设计g3/§6.6明确Phase 1仅FIXED，DISCOUNT/REALTIME的冻结结算价派生仍保持原有范围和链接TODO。此次只修复价格展示、商业条款录入和折扣准入；不将商业条款保存成功当作非FIXED履约发布闭环。不自动补写旧L1，不修改测试环境商品/报价状态，不部署。

## 7. 验证矩阵与门禁

- 服务单测：有SKU建议价且无L1的列表、L1与SKU价不同、0/null/SKU缺失、原L1兼容；DISCOUNT创建/改价在请求提示价缺省/伪造/0时使用权威SKU正价，SKU非正时拒绝且无写入/事件；FIXED保留9500及原评分/版本行为。
- HTTP/JSON契约：新字段与旧字段同时存在且语义不同；请求兼容字段可缺省，ServiceException稳定错误码与文案；字段Schema注释匹配DDL。不能只断言反射字段名。
- 数据库边界：真实MySQL的 `suggested_sale_price` 为NOT NULL且CHECK>=0；null/负数与SKU缺失使用单测构造，集成测试用合法0模拟缺少正销售建议价。
- 真实MySQL+Liquibase：创建并分页查合作商品，验证新字段与SKU表一致、旧L1缺失不阻断新字段；伪造提示价不绕过SKU无效价格、失败事务不写Offer/不改版本；改价成功仍只改身份并按既有事件生成通用定价版本；批量[合法行,建议价0折扣行]失败时连同先前插入身份及同步定价重算全部回滚。用独占测试数据库/容器，不复用pro143库。
- 架构：运行SupplyChainModuleArchitectureTest。
- 真实Vue SFC/API回归：销售建议价与市场价/L1不同；无L1仍显示96.00且DISCOUNT改价请求正常；市场价10000/建议价9600新增提交9600；0/null展示及DISCOUNT阻止写入；固定9500保留；试算86.40；新字段缺失不读取旧价；验证表格模板与实际API请求，不只测试复制的公式。
- 前端修改文件ESLint/格式、全仓既有Node测试、test模式构建与类型检查。类型检查如存在历史错误，以相同环境的修复前基线比较并如实报告，不以“无新增”宣称类型检查全绿。
- 每端新增测试先失败，再实现；保存RED/GREEN日志与最终测试计数。独立规格/质量审查通过后安全同步后端工作树变更至当前目录，保留用户AGENTS与既有排障记录，再完成受影响最终验证。
