# 供应商合作商品独立上下架与有效供货价设计

> 日期：2026-10-11。用户已同意本文业务规则并要求先审查方案再实施。状态：按用户最新要求取消迁移/启动补偿；修订及实现已通过独立规格和质量复审，自动化门禁已执行，失败项修正并复验通过，证据见计划及集成测试记录。引入局部RC以保证同步重算新视图，不修改全局事务配置。
> 本文取代 09-02 管理端 REST a7「新增即上架」、09-22 有效供货价「身份列回退」以及 10-03 发布设计 §8.6「仅按履约状态显示上架/重新上架」。历史已发布版本、报价凭证和订单冻结值不回写。

## 1. 核心业务规则

1. **平台与合作商品上下架彻底解耦**：平台 SPU/SKU 状态与供应商 Offer 状态分别独立维护。平台商品上架只提供合作准入与可售前提，绝不级联上架供应商 Offer。
2. **新增合作商品默认下架**：新增合作商品初始状态统一为 `SUSPENDED`（下架）。保存合作商品仅建立合作关系并记录录入报价，不等于可履约发布；未退役唯一约束、评分默认值、供货范围校验保持。
3. **正式上架唯一编排**：唯一正式上架编排为 `SupplierOfferPublicationService.listOnShelf`。必须校验：供应商 ACTIVE、平台 SPU/SKU ACTIVE（可售）、已发布当前连接器在适配器白名单、SKU 所需主能力在连接器版本中启用、金额/数量/执行画像合法。库存自动开通、版本冻结、外部编码绑定、Offer 状态置为 PUBLISHED 和定价重算事件发布必须在同一 `supplyChainTransactionManager` 事务内完成；失败全回滚。
4. **旧 PATCH 入口安全收敛**：旧 PATCH 接口若传入 `status: PUBLISHED`，必须直接委派给 `listOnShelf` 正式上架编排，严禁绕过校验直接更新数据库状态；PATCH `SUSPENDED` 执行下架并发布定价依赖事件，不删除履约版本、报价和绑定；`RETIRED` 继续走移除流程。
5. **上下架按钮由状态驱动**：合作商品已上架行（`PUBLISHED`）显示「下架」；已下架行（`SUSPENDED`）显示「上架」。所有已上架行额外提供「发布变更」操作（支持连接器切换、履约版本过期或改价变更发布），调用发布编排；不能把重新发布混同为下架。
6. **改价先保存待发布变更**：改价仅修改合作商品待发布身份列（草稿单价），新单价不参与正式定价。若已有生效旧版本，继续以旧版本作为供货成本和履约依据；待发布变更发布成功后原子切换生效。改价失败或发布失败绝不破坏旧版本。严禁将已有 Offer 的 `platformSkuId` 篡改为另一 SKU。
   - 新增下架合作关系及商业草稿保存不发布正式定价依赖事件，不新增正式定价版本；正式发布、上下架/移除及生效依赖变化才触发同步重算。避免无关的下游定价故障阻断草稿保存。
7. **正式有效供货价严选标准**：正式有效供货价必须同时满足结构有效性：Offer PUBLISHED、供应商 ACTIVE、版本与 Offer 归属及当前指针一致、版本有效期 `[validFrom, validTo)`、连接器归属一致且当前版本仍 PUBLISHED、连接器 ACTIVE、适配器白名单有效、当前版本所需能力有效、库存来源 ACTIVE 且类型为 REMOTE_ON_DEMAND、平台 SPU/SKU ACTIVE。一期正式定价还要求候选满足购买数量 1 的最小/最大数量及数量步长；从满足条件的候选版本中取冻结单价最低值；绝不回退身份列，也不因待发布字段漂移排除有效旧版本。
8. **无有效供给阻断交易定价**：无有效供货价时返回空（前端展示“暂无有效供货价”）；既有定价计算按 `DEPENDENCY_MISSING` 阻断新报价。0 分保留现有展示与交易不可售规则；`REALTIME`/`DISCOUNT` 正式发布继续按现有一期范围拦截。
   - 有效供给恢复后，三层当前定价身份随新版本切换为 `READY` 时必须显式持久化 `unavailable_reason=NULL`。MyBatis 普通 `updateById` 忽略 NULL，不能据此宣称旧依赖失效原因已清除；正常上下架、发布变更及依赖状态恢复重算都遵守此不变量。
9. **依赖失效安全阻断**：供应商暂停/拉黑、连接器退役或指针切换时，读侧立即阻断受影响版本的新交易与有效供货价计算；同步按 SKU 去重发布定价依赖事件。系统保持 Offer 自身上下架状态，不自动恢复运营主动下架商品，严禁篡改在途订单与已签发报价的不可变冻结值。

## 2. 单一读模型与前端契约

- **合作商品状态展示（2026-10-20 修订，用户已确认）**：状态列直接按前端 `OfferStatusEnum` 映射，不依赖 `supply_chain_offer_status` 系统字典。`PUBLISHED` 显示绿色（success）「已上架」、`SUSPENDED` 显示灰色（info）「已下架」；兼容 `DRAFT` 显示灰色「草稿」、`RETIRED` 显示灰色「已移除」（正常列表不返回已移除关系）。`undefined`、`null`、空字符串显示 `-`；未知非空状态显示原始状态码并用 info 标签，不推断上下架或赋予发布操作。映射函数集中放在前端 `detail/utils/fulfillment.ts`，由真实列表模板调用。修复仅涉及展示，不修改 API、数据库、通用 DictTag、上下架及「发布变更」行为，无需后端配套发布或字典缓存刷新。
- **履约状态重命名与语义**：`fulfillmentStatus` 表达该 Offer 身份列与当前发布版本的差异：`NOT_CONFIGURED`（未发布版本）、`READY`（已发布且无待发布变更）、`STALE`（有待发布变更）。前端表格列名展示为「商品履约配置」，`STALE` 标签为「待发布变更」，明确其为单商品履约版本就绪度，不代表供应商整体配置状态。
- **列表 DTO 增加发布资格诊断**：`OfferListItem` 追加字段：
  - `canPublish: boolean`（是否满足发布前置条件）
  - `publishBlockedReason: String`（不可发布时的中文阻断原因；若可发布则为空）
  - 计算依据：供应商状态、平台商品可售性、连接器状态、适配器白名单、SKU 所需能力、一期 FIXED 模式、外部编码及金额数量。
  - 该计算为纯只读，不创建库存、不改变状态、不访问外部网络。
- **按钮交互守卫**：
  - 「下架」按钮始终允许对已上架且未退役的 Offer 点击。
  - 「上架」与「发布变更」按钮在 `canPublish === false` 时置灰禁用，并通过 Tooltip 展示 `publishBlockedReason`。后端正式接口做最终硬校验拦截。
- **价格展示统一**：合作商品列表继续展示供应商录入的报价身份列；平台商品列表最低有效供货价与交易定价计算共用统一的有效供给解析器。

## 3. 独立方案审查四大闭环规范

### 3.1 闭环一：技术端发布接口守卫收敛
- **背景与风险**：技术端接口 `SupplierConfigurationAdminController.publishOffer` 底层调用 `SupplierOfferPublicationService.publish`。原实现仅检查了连接器当前版本为 PUBLISHED，遗漏了连接器状态 ACTIVE 校验与适配器白名单校验，存在通过技术端绕过业务守卫发布不可用连接器的风险。
- **收敛规则**：
  1. `SupplierOfferPublicationService.publish` 与 `listOnShelf` 统一共享连接器及适配器校验：
     - 检查连接器状态等于项目现有连接器 ACTIVE 常量（存储值 10，禁止凭空引用不存在的 ConnectorStatus 枚举），否则拒绝发布；
     - 检查 `adapterTypeAllowList.isAllowed(connector.getAdapterType())`，否则拒绝发布；
     - 严格校验平台 SKU 可售性、主能力匹配、所有版本及库存来源归属。
  2. 技术端发布与业务端上架在供给有效性守卫上保持 100% 对齐，杜绝特权绕过。

### 3.2 闭环二：路由与定价资格统一（结构有效性）
- **背景与风险**：此前定价端（`EffectiveSupplyPrice`）只检查 Offer 状态与时间窗口，未校验连接器/库存，且存在身份列回退漏洞；路由端（`SupplierRoutingApplicationService.resolveOffer`）虽然校验了连接器/库存，但缺少适配器白名单与能力检查。两者判定口径不一致，会导致“定价成功选出最低价，下单路由却因连接器/库存问题拒单”，或“定价被阻断但路由放行”。
- **收敛规则**：
  1. 建立统一定价与履约供给有效性判定规范（结构有效性 Structural Validity）：
     - `OfferStatus == PUBLISHED` 且 `SupplierStatus == ACTIVE`；
     - `currentVersionId` 非空且版本归属该 Offer；
     - 当前时间处于版本 `[validFrom, validTo)` 内；
     - `ConnectorStatus == ACTIVE` 且 `ConnectorVersionStatus == PUBLISHED` 且等于连接器 `currentVersionId`；
     - 连接器适配器在 `adapterTypeAllowList` 白名单中；
     - 冻结版本主能力必须匹配 SKU 当前履约类型；主能力及执行画像实际要求的查询/回调能力在连接器版本中启用；
     - `InventorySourceDO` 为该供应商与该 SKU 归属、`status == ACTIVE` 且 `sourceType == REMOTE_ON_DEMAND`；
     - 平台 SPU 与 SKU 处于 `ACTIVE`（可售）状态。
  2. **定价端**：完全移除身份列回退，仅对满足上述全部结构有效性条件的候选版本取最低价；无合法候选则返回 `null`。批量查询时采用候选集合批量加载关联实体，避免 N+1 查询。
  3. **数量口径**：结构资格与数量资格分别封装，共用同一谓词。正式三层定价及平台最低有效供货价按一期支持的数量 1 过滤 `[minQuantity,maxQuantity]` 与 `quantityStep`；该数字复用现有一期数量常量。合作商品身份报价仍按录入值展示。最低起购量大于 1 的 Offer 可以配置/发布，但不能成为一期一件订单的正式成本；不擅自改写其起购量。
  4. **路由端**：复用结构资格及上述数量谓词，传入订单实际购买数量，再叠加自然日限额/配额；定价和路由不得各写一套资格规则。补充「A 单价95起购2、B 单价100起购1」用例，正式成本必须为100；仅A时无有效成本。

### 3.3 闭环三：连接器切换后保留「发布变更」操作
- **背景与风险**：当供应商切换了已发布连接器或升级了连接器版本时，已上架合作商品的旧版本仍绑定在旧连接器上。若合作商品未发生商业字段（价格、外部编码）漂移，前端原逻辑可能仍认为是 `READY`；若前端仅在已上架时提供“下架”，运营将无法在已上架状态下将商品重定向并发布至新连接器。
- **收敛规则**：
  1. 前端 `ProductList.vue` 操作栏按以下状态清晰分流：
     - **已上架行（`status === 'PUBLISHED'`）**：
       - 提供 **「下架」** 按钮：调用 `patchOffer(..., { status: 'SUSPENDED' })`；
       - 同时提供 **「发布变更」** 按钮：调用 `listOfferOnShelf` 编排。
     - **已下架行（`status === 'SUSPENDED'`）**：
       - 提供 **「上架」** 按钮：调用 `listOfferOnShelf` 编排。
  2. 无论是「上架」还是「发布变更」，均绑定统一的发布资格：当 `canPublish === false` 时禁用并 Tooltip 提示阻断原因。
  3. 连接器升级或切换后，运营可以直接在列表点击「发布变更」，系统将自动绑定最新已发布的连接器版本，冻结并生成新的商品履约版本。

### 3.4 闭环四：同步重算的锁顺序与并发事务规范
- **背景与风险**：连接器发布/退役、合作商品上架/改价发布、定价依赖事件消费等多线程并发执行。若获取数据库行锁（`FOR UPDATE`）的顺序不一致，会导致 MySQL 发生死锁（Deadlock）。
- **收敛规则**：
  1. **供应商写操作先取得供应商互斥锁**：Offer 上下架/商业编辑/移除/发布、库存激活和连接器发布/退役，修改子对象前先锁供应商。只有编码时允许预读定位 ID，但预读内容不用于准入。
  2. **发布决策使用当前读**：默认 RR 下普通预读可能已建立历史快照；供应商锁不会刷新快照。发布时连接器、当前版本及能力等可变依赖使用锁后当前读（Mapper Lambda + `FOR UPDATE`），重新核对指针、归属与状态；不得使用预读旧对象或以普通快照冒充当前读。子锁按 CredentialSet → Connector → ConnectorVersion/Capability → Offer → InventorySource 取得；技术端与业务端入口都覆盖，不依赖注解在自调用时改变隔离级别。
  3. **发布事务内重算**：生命周期写入口（商业编辑/上下架/移除/发布、连接器发布/退役、库存激活）显式使用READ_COMMITTED，避免供应商锁等待前建立的RR快照污染随后普通读定价。所有上述生命周期入口在第一条业务读写前检查实际事务隔离；若加入一个非READ_COMMITTED既有事务（包括隔离上下文未显式标记的默认RR）必须拒绝，不能靠自调用注解切换隔离；校验实际事务隔离上下文，直接无事务单测不承担数据库隔离证明。仅这些入口调整，不修改共享事务管理器或全局隔离。共享资格谓词接收已经校验的事实；重算查询必须能看见本事务新版本/状态/库存绑定，不使用 REQUIRES_NEW 绕过未提交写入。一般列表及交易资格读保持现有独立只读快照边界；写守卫与读解析不能机械混用锁策略。
  4. **定价锁**：人工批量平台/分销商/项目定价与首版平台默认定价初始化，先收集目标 SKU、去重并按 ID 升序取得平台定价身份锁，再读取父配置/计算并发布子层版本；这些批量写入口同样使用局部 READ_COMMITTED，第一条业务读写前拒绝非 RC 外层，防止锁等待前建立的 RR 快照在锁后读取旧父版本或旧供给。沿用商品/目录原有准入锁，不将它们误当作定价锁。校验与返回仍保持请求顺序，锁顺序不受请求顺序影响。多 SKU 事件先去重并按 platformSkuId 升序处理，每 SKU 的定价身份按平台 → 分销商 → 项目层级与主键升序锁定。`PlatformSkuBatchLock` 实际锁的是商品行，不能直接拿它锁定价；这里只复用排序原则，不新增商品行排他锁。持定价锁的解析器不反向取得供应商/连接器排他锁。
  5. **并发验证**：真实 RC 两事务测试：事务B先定位，事务A退役并重算后提交，B等待供应商锁后必须拒绝发布；独立验证已有RR外层调用在第一条业务读写前拒绝、连接器升级后发布与同步重算均读取新版本；验证相交多SKU批次、发布与连接器退役、重算与平台商品修改均能完成且历史冻结值不变。
  6. **默认初始化外层事务**：`ProductCatalogCommandService.createProduct/updateProduct` 同步触发平台默认初始化，必须同样局部 RC、入口第一条业务读写前拒绝非 RC 外层；初始化监听器沿用该事务。不得用 `REQUIRES_NEW` 绕过未提交的新 SKU 或破坏复合保存原子性。评估并回归商品复合保存、首版初始化、批量默认定价、对应 HTTP/RPC 契约及架构约束，其他商品写入口及共享事务配置保持既有行为。
  7. **完整外层批次**：分销商关联的 `BuyerProductSelectionBatchTransactionalWorker.executeBatch` 与项目关联的 `ProjectListingCommandService.addProducts` 同步执行行内通用定价，其外层同样局部 RC、入口拒绝非 RC；在逐行初始化/定价前按整批 SKU ID 升序预锁平台定价身份，不能由各单行调用分别加锁。商品复合更新在发出任何定价事件前，合并默认初始化和基础价变更 SKU 集合、升序预锁，再保留各事件语义。共用专门的定价锁工具；该工具不锁商品行，不修改数据库或启动配置。
  8. **独立继承初始化**：`initializeBuyerProduct/initializeProjectListing` 也可以在自动目录刷新等事务外门面被独立调用，不能仅依赖关联批次的预锁。这两个入口自身使用局部 RC、入口拒绝非 RC，并在读取父定价版本及锁定子层定价身份之前先锁当前 SKU 的平台定价根；加入关联批次时复用已持有根锁，不另开事务。保证等待生命周期重算后读取最新父版本与供给，禁止旧视图覆盖新定价。
  9. **锁后重新加载计算输入**：未持有 SKU 行锁的分销/项目批量定价、独立继承初始化和生命周期同步重算，锁前 SKU 对象只定位。取得全部平台定价根锁后以 RC 普通读重新加载 SKU 基础价，再读取父版本并计算；RC 不会刷新 Java 旧对象。禁止逆向取得 SKU 排他锁。回归商品基础价变更尚未提交时，初始化等待根锁后必须使用新市场价/建议售价及新父版本。
     - 真实并发回归确认 MyBatis 会话一级缓存也会保留锁前 `selectById` 结果。锁后重读前须清除本次供应链 SqlSession 的一级缓存，再执行普通读取；仅限定当前会话，不调整全局缓存/隔离配置，不反向加 SKU 锁。专用读取工具使用显式 `supplyChainSqlSessionFactory`，确保不触及其它独立进程的数据源。

### 3.5 外部商品编码占用预检与管理端错误契约（2026-10-22）

用户确认仅修改后端，沿用现有前端错误展示。新增、兼容批量新增与商业编辑均须检查同供应商外部编码占用：在既有供应商行锁及局部 READ_COMMITTED 事务内，通过 MyBatis Plus Lambda 按 supplier_id、external_sku_code 和 status != RETIRED 查询，编辑排除自身 Offer。字符串相等由数据库裁决，与现有唯一索引排序规则保持一致，不新增编码归一化或修改历史数据。草稿、上架、下架均占用；退役释放沿用057迁移，无DDL变更。

批量新增按请求顺序逐行预检及写入。同批后续重复可读取本事务前面新建的身份，任何冲突抛异常并使整批回滚，禁止返回部分成功。新增预检位于SKU重复检查与INSERT之间；商业编辑预检在修改身份字段前执行，自身编码不变允许保存。预检查询最多返回一条占用身份，并读取其平台SKU编码用于明确提示；SKU缺失时以Offer业务编号定位，不泄露内部数据库主键。

新增错误常量 `SUPPLIER_OFFER_EXTERNAL_SKU_CONFLICT`，编号 `1_050_001_183`，登记 `DO_NOT_RETRY`。文案模板为 `供应商商品编码「{}」已被{}占用，下架商品仍占用编码，请核对后修改。`，正常预检中第二参数为 `合作商品「SKU_xxx」`；兜底无法取得占用详情时为 `其他合作商品`。错误由 `ServiceException` 经现有 `GlobalExceptionHandler` 返回HTTP200、CommonResult业务code=1050001183、中文msg和data=null，保留原追踪协议。前端现有service.ts对code=500隐藏业务msg、对普通业务code以ElNotification.error标题展示msg，因此不能仅修改500的msg，不能返回HTTP409/500绕入网络错误分支；不修改前端或共享异常处理器。

数据库唯一键 `uk_sc_supplier_offer_external_sku` 保留最终裁决。在本服务INSERT/UPDATE的DuplicateKeyException边界，仅将因果链中MySQL错误1062、SQLState=23000且明确命中该索引名的错误转换为上述业务异常，保留原异常因果；不得仅按包含索引名判断，避免其它错误或重复值文本误命中。兜底文案不依赖异常后再查库。其它唯一键冲突原样上抛。服务层不额外打印异常；现有HTTP终结边界记录一次单行WARN，不输出系统异常堆栈。

验证要求：单测覆盖新增/编辑预检、精准异常识别及其它异常不误转；真实MySQL/Liquibase覆盖下架占用、退役释放、跨供应商复用、自身排除、批内重复与后续冲突全回滚、数据库大小写/重音等比较规则、供应商锁下并发仅一个成功；HTTP契约使用真实Controller、业务服务与异常处理器，验证HTTP200、专用code、明确msg、data=null及原TraceFilter响应头。供应链普通/架构与适用集成/契约门禁必须通过，步骤及自动化/实机证据分别维护于 `docs/集成测试.md`。本变更不部署，不重放用户写请求。
