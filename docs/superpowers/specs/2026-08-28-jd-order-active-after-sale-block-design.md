# 京东订单活动售后阻断设计

## 1. 背景与目标

`JdOrderFulfillmentJob#execute` 会扫描已支付、待发货的 `JD` / `MIXED` 商城订单，并由
`JdOrderFulfillmentServiceImpl` 创建履约账本、调用京东 VOP 下单。现有逻辑主要依据京东订单项的
`after_sale_status` 判断是否可以履约，无法覆盖 `MIXED` 订单中非京东商品正在售后的场景，也无法直接表达
“售后单仍未处理或处理中的整单阻断”规则。

本次调整的目标是：一笔商城订单只要存在任意一张未结束的售后单，本次京东履约下单就必须暂缓；售后进入
终态后，由后续调度重新判断并继续满足条件的京东商品履约。

## 2. 状态口径

活动售后统一复用 `AfterSaleStatusEnum.APPLYING_STATUSES`，包括：

- `APPLY(10)`：申请中，尚待商家处理；
- `SELLER_AGREE(20)`：商家已同意，售后处理中；
- `BUYER_DELIVERY(30)`：买家已退货，售后处理中；
- `WAIT_REFUND(40)`：等待平台退款，售后处理中。

`COMPLETE(50)`、`BUYER_CANCEL(61)`、`SELLER_DISAGREE(62)`、`SELLER_REFUSE(63)` 均为终态，不再作为
“活动售后”阻断整单。已完成退款的商品是否继续履约，仍由订单项 `after_sale_status` 和既有履约快照调整逻辑决定。

## 3. 阻断范围与时机

阻断按商城主订单 `trade_order.id` 生效，不区分售后商品的供应商。因此，`MIXED` 订单中的非京东商品只要存在
活动售后，也暂缓整笔订单内京东商品的 VOP 下单。

为覆盖调度扫描、历史 `INIT` 履约账本和人工指定单号三条入口，活动售后检查放在以下位置：

1. 创建初始京东履约账本前：存在活动售后时不创建账本；
2. 构造京东请求上下文前：已有 `INIT` 账本时暂缓，并记录可重试错误码；
3. 原子认领 `INIT -> SUBMITTING` 前：在短事务内再次检查，缩小售后并发创建与外部下单之间的竞态窗口。

售后查询通过 `AfterSaleMapper` 的 MyBatis Plus Lambda 条件实现，按 `order_id + APPLYING_STATUSES` 判断是否存在，
不新增字符串列名或散落的状态魔法值。

由于该判断位于最高每批 100 条的定时扫描和提交前复核路径，`trade_after_sale` 增加
`(tenant_id, order_id, deleted, status)` 联合索引，避免按主订单查询活动售后时反复扫描整张售后表。迁移脚本为
`sql/mysql/2026-08-28-trade-after-sale-order-status-index.sql`。

## 4. 状态机与错误处理

- 活动售后命中时，尚未创建的履约账本保持不存在；下一轮调度可在售后终结后正常创建。
- 已存在的 `INIT` 账本命中活动售后时保持 `INIT`，使用 `ORDER_AFTER_SALE_PENDING` 作为安全错误码并按既有退避策略重试。
- 已进入 `SUBMITTING`、`UNKNOWN` 或 `SUBMITTED` 的订单不由本规则回退状态，继续沿用既有查单与售后取消流程，避免结果未知时重复下单。
- 售后明细、收件信息及京东原始报文不得写入日志；任务仍只记录订单或履约账本标识和安全错误码。

## 5. 验证边界

联调需覆盖纯京东订单、`MIXED` 订单非京东商品售后、已有 `INIT` 账本、售后终态恢复以及人工指定单号任务。
具体步骤见 `docs/集成测试.md#6-京东订单活动售后阻断联调`。

## 6. 最终子订单全量售后取消规则

京东 `cancelOrder` 的最小操作粒度是最终子订单。为避免一个最终子订单内仍有正常履约商品时误取消整张子订单，
取消任务按 `trade_order_fulfillment_order` 聚合判定，不再以“任一售后商品命中子订单”作为取消条件。

一个最终子订单只有同时满足以下条件，才允许为其登记并执行取消任务：

1. 子订单及其商品关系均为当前有效快照；
2. 子订单至少包含一条有效商品关系；
3. 每条有效商品关系对应的商城订单项均绑定售后单；
4. 每张售后单均处于 `AfterSaleStatusEnum.APPLYING_STATUSES`；
5. 每张售后单的申请数量均等于对应商城订单项数量，即整条订单项发起售后。

只要任一有效商品关系不满足上述条件，该最终子订单本轮不得创建、恢复或执行取消任务；已存在但尚未成功的任务应关闭。
单商品子订单天然满足“全部商品售后”时，继续沿用原有取消行为。若后续其他商品补充发起售后，任务重算会在全量条件
首次满足时为该子订单内各售后单登记任务，并由同一子订单级认领逻辑合并为一次京东取消调用。

取消任务在创建时和调用京东前均须复核全量条件。创建后的售后关闭、拒绝或子订单关系刷新，可能使条件失效；此时不得
仅依据剩余的一张活动任务继续取消整个子订单。已经取消成功的供应商订单不可逆，仍保留成功结果，不尝试恢复。

## 7. 全量取消验证边界

联调需覆盖最终子订单单商品、多个商品部分售后、多个商品全部售后、补充售后后触发取消，以及调用京东前售后关闭的
并发复核场景。具体步骤见 `docs/集成测试.md#64-京东最终子订单全量售后取消联调`。

## 8. 批量履约支付等待窗口

`JdOrderFulfillmentJob#execute` 批量扫描京东履约候选订单时，只允许支付时间早于本次扫描时间 30 分钟的订单进入
后续履约流程。支付未满 30 分钟以及恰好满 30 分钟的订单本轮均跳过，由后续调度在等待窗口结束后按原条件重新扫描。

该条件仅增加在 `selectJdFulfillmentCandidateList` 的候选订单查询中，不改变订单状态、配送方式、来源类型、京东商品、
订单项售后和已有履约账本等既有判断，也不影响 `jdOrderFulfillmentByOrderNoJob` 人工指定单号入口及拆单、物流、取消任务。
等待分钟数由 Java 常量统一维护，查询使用本次扫描计算出的支付时间上限，避免在 SQL 中散落业务魔法值。

具体联调步骤见 `docs/集成测试.md#65-京东批量履约支付等待窗口联调`。
