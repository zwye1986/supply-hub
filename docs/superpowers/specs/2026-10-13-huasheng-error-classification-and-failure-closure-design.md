## 1. 目标、证据与范围

### 1.1 已确认的目标

1. 区分接口操作失败与订单履约失败，不将全部非零错误统一拖入未知恢复和人工。

## 2. 方案比较与推荐

### 2.1 推荐：华昇专属决策，保留封闭映射

在现有华昇协议事实、FlowPolicy、Lifecycle、Runner 内增加阶段化错误决策和可信失败收敛。复用已有资金服务、Timer、进程互斥锁、异常 Case 与身份快照；新增必要的人工命令审计，不建立通用工作流引擎。

优点：可以同时检查端点、历史发送、退款、提卡、资产和金额，资金决策不暴露给运营填表；保持现有连接器 v1 可用。代价：需要针对华昇维护纯逻辑规则及管理端处置契约。

### 2.2 不推荐：开放错误／状态映射配置资金动作

只把错误码映射到 REJECT 或 RETRY_SAFE 无法表达“同一错误在首次 PLACE 与 TAKE 后意义不同”，也无法证明退款和零交付；会与当前封闭发布守卫冲突。本轮不采用。

### 2.3 不推荐：全部保留人工，仅增加人工释放按钮

改动小，但参数错误仍长期冻结，价格冲突单仍只能人工等待；直接释放按钮还绕过供应商原单事实。本轮只提供基于可信核实结果的失败确认，不提供强制资金按钮。

## 3. 不变量与状态模型

### 3.1 资金及受理不变量

- 永久受理键、首次报价、项目商品身份、Offer／Connector 版本、商品、数量、目标及供应商 billno 均不可改写。
- 已 ACCEPTED 的受理回执保持 ACCEPTED，不因履约失败改为受理 REJECTED；原同参重放仍返回同一回执和订单。
- 失败只释放本单预留的 remainingAmount，通过 `FundReservationService.releaseByReference`，不按供应商价格计算退款，不直接访问账户／账本 DAL。
- 任何已提交资金、已交付或待核资产、已获卡观察、成功终态及相反终态冲突，均阻止失败释放；金额差异例外只适用于可信零交付失败，不适用于成功确认。
- 同一失败重放不得新增状态日志、重复递增 detailVersion、重复结案或重复 RELEASE 流水。

### 3.2 最小状态扩展

供应商 BOrder 增加 `CANCELLED=60`，DDL COMMENT 与 CHECK 同步前向扩展；现有 50 仍为 FAILED，不复用公共订单的取消码。

可信取消后的目标组合：

- BOrder：CANCELLED，fulfilledQuantity=0，activeFlag 显式清为 NULL，completedAt 写入。
- Operation：FAILED，结果仍为现有 REJECTED；协议事实保留 CANCEL，不扩展通用 OperationOutcomeClass。
- FulfillmentRequest：FAILED。
- 平台 SupplyChainOrder：FAILED，CARD_FAILED；不是平台 CANCELLED，也不是售后退款。
- 项目 HTTP/RPC：orderStatus=FAILED、fulfillmentStatus=FAILED，追加可选稳定失败原因；不增加项目履约 CANCELLED 枚举。
- 资金预留：remaining=0，released 增加本次剩余冻结，committed 不变。

可信 FAILED、无副作用拒绝或第 5.4 节的可信未建单均对应 BOrder FAILED，其余失败组合相同；可信未建单的 fulfilledQuantity=0、activeFlag 显式清为 NULL、completedAt 写入。不新增平台 NOT_CREATED 状态，不伪造供应商 orderSn、CANCEL 或退款成功事实。所有 BOrder 终态判断、筛选、管理 DTO 及迟到回调防重须认识 CANCELLED。

### 3.3 原因记录

分开保存三个事实：供应商原始状态／错误码；平台稳定失败或人工原因；独立价格差异。不能把金额不匹配伪称为供应商取消原因。

拟使用稳定原因：`HUASHENG_SUPPLIER_CANCELLED`、`HUASHENG_SUPPLIER_FAILED`、`HUASHENG_NOT_CREATED`、`HUASHENG_REQUEST_REJECTED`、`HUASHENG_AUTH_UNAVAILABLE`、`HUASHENG_PRICE_MISMATCH`、既有准备失败／恢复到限／事实冲突。

可信未建单使用 `HUASHENG_NOT_CREATED`，说明为“供应商未建单，订单履约失败”；原始拒绝码、退避查询记录及判据分别保存，不把未发生的退款写成成功。缺少符合条件的首次创建拒绝、有效查询不足 4 次或安全检查不通过时，不得使用此终结原因。

供应商未给具体取消说明时只记录“供应商返回已取消”，同时保存 expireTime／refundTime 等已获得的事实；不得凭时间相同断言超时取消。

稳定原因的归属：可信 QUERY CANCEL 对应 `HUASHENG_SUPPLIER_CANCELLED`；QUERY／正式回调 FAILED 对应 `HUASHENG_SUPPLIER_FAILED`；首次创建拒绝候选经四次有效 7014 对应 `HUASHENG_NOT_CREATED`；有完整无副作用证明的 51／前置安全 66／初始授权 4002、4003 对应 `HUASHENG_REQUEST_REJECTED`；初始授权暂时故障耗尽预算对应 `HUASHENG_AUTH_UNAVAILABLE`。单纯有效金额差异使用 `HUASHENG_PRICE_MISMATCH`；身份、数量、资产或历史成功矛盾仍为事实冲突，不归为价格差异。

## 4. 错误分类规则

### 4.1 决策输入与所有权

专用协议层输出端点、整数原始 code、受控安全原因、供应商 traceID、物理调用证据及是否开始业务请求。应用层结合持久发送历史、原单／资产／预留／Case 状态作决策。

分类只在华昇纯决策中维护，优先扩展现有 `HuashengFlowPolicy` 和不可变事实，不新增可配置“任意错误直接退款”表。规则输出使用封闭动作：失败候选、重新授权、发送前重试、原单核实、人工保留；最终动账只在锁后生命周期执行。

“没有业务副作用”的证明必须覆盖本单全部相关历史尝试，不能仅依据本次 TOKEN 未发送业务、单次 `wasBusinessCallStarted=false` 或日志缺失。`businessSendPossibleAt` 是保守 marker，不等于物理发送，也不能单独证明已经建单。历史证据缺失、超时、解析失败或无法关联时关闭无副作用快捷路径。

### 4.2 可以直接失败的范围

1. 初始授权返回 4002／4003，且能证明该原单从未发起创建业务请求：记录账号／绑定拒绝，失败释放。
2. 51 明确参数校验失败，或 66 明确前置安全配置拒绝，并能证明没有历史未核实请求、原单和资产：失败释放，不原样重试。
3. 初始授权暂时故障耗尽发送前预算，仍证明没有创建业务请求：以授权不可用失败释放，不把它伪装成供应商已退款。

本稿未建单判定的创建拒绝候选范围为首次 PLACE 的 7002／7003／7005／7006／7007／7008／7010／7011／7018／7022，禁止无意义原样重试；此端点／码清单仍随整稿评审，不扩展为任意非零错误。单凭这些码不立即释放，而是进入第 5.4 节的退避查单分支。CONFIRM／TAKE 等已有订单阶段返回同一码，或历史 PLACE 曾有未核实的未知结果，不适用该分支。

第 4 次有效原单查询仍为 7014 且共同安全检查通过时，按已确认的中台规则判为可信未建单并最终失败，不再要求另行取得退款响应或供应商回滚保证。未达到 4 次有效查询而耗尽恢复预算，或事实冲突时，才转 MANUAL 并保留资金；不得把总查询认领次数当作有效未建单次数。

7025 修正查询标识为二选一后再查原单；不改业务身份。发生在已存在原单的确认／取卡阶段，任何前置拒绝只能终止本次操作，不能直接终止整个原单。

4002／4003 的授权端点归属是保守假设，文档未给出端点集合；只有 TOKEN 返回且完整证明未发业务请求才适用快捷失败。若业务端点返回这两个码，按未知业务错误核原单，不因整数码相同直接释放。

### 4.3 61 与 66

- 61 保留门面内的一次刷新和同业务身份重发；新 timestamp／nonce／密文／签名，禁止无限刷新。
- 第二次 61：首次创建前且证明无副作用，按发送前授权预算处理；已有原单或历史风险，则等待授权恢复后查询原单，到限人工。
- 66 的缺字段、签名／解密／密钥配置错误、应用禁用：停止原样重试，记录受控原因及配置告警。
- 66 请求过期：不直接释放已存在的原单；校准时钟，在无历史风险且明确前置拒绝时允许本次请求重新构造一次。仍过期转配置故障，不持续重发。
- 66 重复 nonce：保留原业务单号查询，不能认为原请求未执行。
- 未识别的 66 message 不按自由文本猜副作用，进入原单核实。安全原因只匹配官方固定提示，不持久化任意原始 message。

### 4.4 暂时错误与原单核实

- 4001、50、7001、7004、7009、7013、7017、7024：发送前授权／只读查询可退避重试；已发送的 PLACE／CONFIRM／TAKE 优先核原单，不盲目重复写操作。
- 7012、7014、7015、7016、7019、7020、7021、7023、7101、7203、7204、7302：原单核实，保持 billno／orderSn，不创建新单。7014 的单次不存在不是未创建证明。
- 7301：查询原单后受控重取同一套卡密；不更换业务号或重新购买。
- 7201：暂停 CONFIRM／TAKE，查询取消、退款和提卡事实；码本身不是退款完成证明。
- 7202：恢复已获卡原单事实与资产，禁止失败释放；本轮不增加取消请求端点。
- 7205／7206：原单补偿状态查询；确认补偿持续失败或到限则人工，不假装已退款。
- 未知码、HTTP／网络／解析异常：保守原单核实；不从非零 data 构造订单成功或退款证明。

5001／5002／5004／6001／6002／6004 按目录读取暂时故障处理；5003／5005／6003／6005 按资源／权限拒绝处理。当前标准履约不调用这些目录端点，本轮不扩展目录同步；未来调用不能改变在途订单状态。

目录码目前在协议枚举中仍可为 UNKNOWN；未来目录调用须按整数 rawCode 分类，不以枚举 UNKNOWN 代替业务分类。本轮履约遇到这些码保持未知原单核实。

7017／7019／7020／7023 的官方建议包含原外部幂等业务单号重发。本设计有意采用只查原单：官方建议不等于可验证的永久去重／原子回滚契约，重复交付损失高于延迟损失。真实未建单且初始拒绝不属于候选清单时仍保留资金到限人工，不能用四次 7014 扩大清单。

### 4.5 有界预算与任务持久化

- 复用首发送后 30 分钟、QUERY 20 次、CONFIRM 3 次、TAKE 5 次的既有上限；认领次数与物理 HTTP attempts 分开记录。
- 发送前授权／准备重试最多 3 次总认领，后两次延迟 5 秒、15 秒；只有持久证明本单没有业务副作用才允许再次执行原创建步骤。不能依据异常后空 attempts 重新 PLACE。
- 未建单候选分支单独按 5／15／30／60 秒退避、随后封顶 60 秒；有效 7014 累计满 4 次即失败收敛，不等查询 20 次或等待 30 分钟。查询异常不增加有效次数，继续恢复仍受原 30 分钟截止和 20 次认领上限；普通未知原单查询暂时故障仍按 30／60／120 秒退避并封顶 120 秒，有效 WAIT 间隔保持 30 秒。
- CONFIRM／TAKE 的重试仍由可信原单状态决定，不增加错误码驱动的裸重发。内部一次 61 重发计物理尝试，不额外增加业务步骤认领次数。
- 延迟意图与状态在同一供应链事务写既有 Timer／Outbox；不以内存 sleep 或 afterCommit 回调承担恢复可靠性，不新增通用重试配置层。

本轮保留 3 次总认领、5／15 秒的初始授权预算（不计调用耗时约 20 秒）；取舍是尽快给采购方确定失败、避免长时间占用预留，而不是将暂时故障声明为供应商履约失败。只有完整无副作用证明才可失败释放；无证明仍核原单。延长到 3～5 分钟属于后续产品等待预算调整，本轮不悄然改变。

## 5. 价格差异与可信失败解耦

### 5.1 新在途单的价格保护

身份／数量正确、金额格式有效、无已知或待核资产，但实报与冻结成本不符：保存实报金额与原报价差异，设置结算 MISMATCH，停止 CONFIRM／TAKE，进入“仅查询原单”保护分支，而不是立即停止所有自动核实。

- QUERY 仍 WAIT：只读继续等原单，不确认付款，不新建 PLACE。
- QUERY 为 SUCCESS 或 isTake=Y：转人工，不能自动拿超报价资产或失败释放。
- QUERY 为 CANCEL／FAILED 且退款 SUCCESS、未提卡 N、无资产：可信失败收敛，允许金额差异继续留存。
- 格式非法、身份／数量冲突、资产或终态矛盾：不是单纯价格差异，维持人工／未知保护。
- 查询预算耗尽：转人工，保留采购资金；不能因为“本来应自动取消”自行释放。

未来价格保护须有可判定的稳定原因和持久模式；不能将所有旧 `HUASHENG_FACT_CONFLICT` 一律解释成价格差异或自动恢复。

### 5.2 可信取消／失败的锁后检查

以下条件适用于取得供应商原单终态的失败收敛，不要求第 4.2 节的无副作用拒绝或第 5.4 节的可信未建单伪造 code=0 或退款成功。无副作用拒绝与可信未建单须另行验证各自完整证明，并共用下列资产、代次、资金及幂等检查；不能仅凭非零错误码绕过它们。

供应商终态条件按此顺序判定：

1. QUERY 响应正式解析成功且 code=0，或正式回调完成验签、解密及协议校验；冻结供应商／连接器／billno、已知 orderSn 对应原单。原订购数量从冻结参数／检查点核实；QUERY 的 num 须与之相符，FAILED 回调的 num=0 或省略只表示零交付，不能当作订购数量。
2. QUERY 的 CANCEL／FAILED 明确 refundStatus=SUCCESS、isTake=N；正式失败回调沿已有“零交付、已退款”的协议保证核实。
3. 当前及历史保护证据均无已交付／待核资产、已提卡或成功事实，没有未收敛的反向终态／身份冲突。
4. 没有可继续 CONFIRM／TAKE 的在途资格；结果代次和来源有效，旧执行／旧回调不得越过围栏。
5. 预留只能 RESERVED 且 committed=0；同事实 RELEASED 的完整终态组合只能幂等返回，不重新写状态。资金终态与订单组合不一致转存储异常，不自行修复。

正式回调继续只接受 SUCCESS／FAILED，本轮不新增 CANCEL 回调。供应商取消状态从可信原单查询取得，不能把 FAILED 回调改写为已取消。

上述条件满足时，实报 20000 分与冻结成本 9500 分不一致仅产生差异，不否定原单可信取消；采购释放数额来自自己的 9600 分预留。

成功路径仍要求原报价金额一致、完整 type201 资产及原有安全检查，本轮不放宽成功结算。

### 5.3 同事务写入及冲突留证

扩展现有受控失败收敛入口，不把现有只检查 permit／无资产的 `releaseHuashengRejection` 裸露给管理端。

短事务内统一：锁聚合 → 再核终态／代次／证据 → 写供应商取消或失败 → 写 Request／平台失败 → 写稳定原因与原始观察 → 释放预留 → 使旧 Timer 资格失效 → 写命令完成审计。

显式清 NULL 活动标记，不能依赖 MyBatis Plus 默认跳过 NULL。任意 CAS、账本、原因或证据写入失败全部回滚；业务完成日志仅 afterCommit 记录。

金额差异保留在 BOrder 的 expected／reported 与 settlementStatus=MISMATCH，以及不可变证据中。confirmedSupplierSettlementAmount 不伪造成 0 或 9500 分；供应商实际支付／退款流水仍是独立事实。

自动流程不得伪造运营人员结案。已有 Case 的业务待定解除情况可以追加说明，但其运营审计仍保持待结案；订单终态与 Case 审计状态分别展示。人工失败确认则由真实操作人在同事务结案，历史原因及价格证据保留，不宣称已完成供应商资金对账。

### 5.4 可信未建单的最终失败

此节最终失败语义、查单间隔及第 4 次有效查询阈值已由用户确认。可信未建单是中台依据以下规则作出的履约结论，不是供应商订单主状态，也不是供应商承诺“将来绝不会建单”的事务证明；不能把无条件多次 7014、超时到限、空 orderSn 或本地无资产都归为可信未建单。

判定顺序及有效查询规则：

1. 首次 PLACE 得到第 4.2 节的明确创建拒绝，持久化最早拒绝码及 firstRejectionAt；固定原供应商账号、连接器版本和 outOrderSn，不用新业务号或最新账号查单。此前没有未核实的创建发送、已知供应商订单、CONFIRM／TAKE、成功／资产事实或已提交资金；缺少完整历史时不得启用此分支。
2. 第一次查询在该拒绝结果后等待 5 秒；后续查询在上次终止结果后依次等待 15／30／60 秒，再封顶 60 秒。无异常时累计等待 110 秒取得第 4 次结果，实际时间还包含外呼、调度和落库耗时；不能用“已过去 110 秒”替代四次结果。
3. 只有同一冻结身份及原业务号、正式解析得到 7014、执行围栏有效且已持久化的 QUERY 终止结果，才增加有效未建单次数；四次有效查询都必须为 7014。超时、HTTP／网络／解析故障、50、授权失败等不计有效次数，可按预算继续只读查询，不据此重发 PLACE。门面内 61 刷新后的最终 7014 只计一次；旧代次返回、重复 Timer／消息或同一结果重放不得重复计数。
4. 任一次可信查询或回调查到订单或产生成功／交付事实，即永久退出该候选分支，按已有订单路径处理；不得以后面的 7014 覆盖。第 4 次有效 7014 落库时，锁后复核候选身份、四次事实及共同安全检查，通过即自动最终失败；不足四次而恢复到限则人工保留资金。

最早拒绝、模式、查询序次、有效次数、lastQueryAt／nextQueryAt 和对应不可变终止记录必须持久化，与结果状态及 Timer 意图同事务更新；不能仅保存在内存、重启清零或由客户端传次数。保持历史 checkpoint V1 不变，新增事实的版本化存储须有明确兼容读取；旧单证据缺失不能回填成已查四次。

一旦可信依据有效且锁后无历史成功／提卡／待核资产／已提交资金／反向事实冲突，自动流程或受控人工确认均按最终履约失败处理：BOrder、Operation、Request、平台订单统一 FAILED，平台履约为 CARD_FAILED，记录 `HUASHENG_NOT_CREATED` 及证据来源，恰一次释放本单 remainingAmount，并使旧执行与 Timer 资格失效。不重新 PLACE，不把该结论继续投影为 RESULT_UNKNOWN 或要求人工无限等待。

此路径不要求供应商 code=0、CANCEL／FAILED、refundStatus=SUCCESS 或 isTake=N；这些已有订单终态证明不存在时保持缺失，不造数。它仍必须通过第 5.2 节第 3～5 项的共同安全检查，并按第 5.3 节同事务更新；重复失败幂等返回，相反事实或资金状态不一致保留证据并转异常，不强制释放。

本次不新增供应商核账接口、人工证据附件或风险核销机制，不把中台判据描述成供应商已核账。失败释放后若出现迟到成功／资产等相反事实，保留已有终态及资金流水，进入终态矛盾 Case，不自动重新扣款、再购买或掩盖冲突。原金额冲突实测单已有供应商 orderSn 和 CANCEL 事实，应走可信取消路径，不套用本节。

## 6. 存量人工单的受控入口

### 6.1 范围与两步命令

只支持 HUA_SHENG_ORDER_V1、CARD、quantity=1 的原人工单。使用现有服务进程的 token 管理器和执行互斥锁，不停服，不创建第二个授权客户端。

拟新增管理路径（含 `/admin-api` 网关前缀）：

- `GET /supply-chain/fulfillment-cases/{caseNo}`：查询现有 Case、原单状态、资金处置摘要、脱敏证据及可操作条件；只读，不外呼。
- `POST /supply-chain/fulfillment-cases/{caseNo}/verify`：提交一次原单核实，正文含 actionNo、expectedCaseVersion、expectedGeneration、reason。
- `GET /supply-chain/fulfillment-cases/{caseNo}/actions/{actionNo}`：查询核实任务及可用于失败确认的结果。
- `POST /supply-chain/fulfillment-cases/{caseNo}/confirm-failure`：正文含独立 actionNo、verifyActionNo、expectedCaseVersion、expectedGeneration、reason；不接受外部订单状态、金额、退款勾选或证据文件替代服务端事实。

独立权限 `supply-chain:fulfillment-case:query`、`:verify`、`:confirm-failure`；与现有平台管理员超集一致。真实 ADMIN 操作人来自 LoginUser，客户端不能传 operatorId；核实和动账权限分开，不能借直充 release 权限执行华昇关单。

### 6.2 核实不是恢复购买

核实以同事务命令审计＋持久 Timer 提交，HTTP 成功只表示命令已受理。任务在取得进程互斥锁后，短事务锁定原聚合／Case并生成新代次，再在事务外执行一次原单 QUERY，最后短事务保存结果。

核实最多一次 QUERY 认领，仍允许门面已有的一次 61 重发；不执行 PLACE／CONFIRM／TAKE／取消。同一 Case 同时只允许一个核实意图，使用数据库唯一约束及锁后检查，不只靠进程内去重；核实不重置原自动恢复计数或截止时间。

执行前持久化该 action 的查询已开始标记、执行代次与租约截止时间。Timer 重投或进程恢复发现已开始标记时不得再次外呼；即使恰在标记后、发送前宕机，也按未知处理，不猜测请求未发。核实租约沿既有执行租约设置，持久 watchdog／启动恢复负责检查：到期仍无完整结果则把 action 终结为 UNKNOWN，清除其活动意图，并使该执行资格失效，允许运营提交新的 actionNo；保留旧审计，不把未知任务标为成功。清理只能处理自己仍持有的代次，不能使更新任务失效。

网络不确定、宕机或未持久化结果使该 action 不能用于释放。迟到返回只能留在旧 action 的诊断中，不能重新取得核实资格、替换最近证据或触发释放。若需再查，运营提交新的 actionNo，旧任务不得重放；命令查询返回实际 caseVersion、generation、核实时间及 freshUntil，供后续确认使用。

保存原失败检查点不覆盖，新的原单核实事实单独加密绑定 action／Case／Operation／冻结版本／代次；资产证据不明时关闭失败确认，不解密卡密给管理端。查得 WAIT／SUCCESS／退款未完成／未知，仅保存核实结论，不自动推进购买或释放。

有符合第 4.2 节的初始拒绝及完整历史时，原单核实可继续累计第 5.4 节的有效未建单查询；每个 action 仍只认领一次 QUERY，提交过早由持久 Timer 等到 nextQueryAt，不能用运营连续点击绕过退避间隔。仅合规、持久化且当时围栏有效的不同结果参与累计；旧单无法还原初始拒绝时不能仅凭四次核实 7014 关单。人工核实累计达到四次时只提供失败确认资格，仍由真实操作人提交第二步关单命令，不在核实动作中自动动账。

### 6.3 失败确认的证据与幂等

只能使用同 Case 最近一次成功持久化、生成后不超过 5 分钟、同当前代次且未被回调／状态变化失效的核实结果；提交后在锁内按依据类型复核：已有订单取消／失败执行第 5.2 节全量检查，可信未建单执行第 5.4 节初始拒绝、四次有效查询及共同安全检查，不错误要求退款终态。旧 JSONL／截图是调查材料，不是动账证据；单次 7014 或无合规初始拒绝的累计查询，不提供可信未建单确认资格。

先校验当前权限与 Case 访问范围，再查 actionNo 的既有审计；命令指纹绑定真实 actor、命令类型、Case／原单身份及全部业务参数。相同 actionNo 和完全相同指纹返回原受理／执行结果，不外呼或动账；同号异参拒绝，不能因已完成动作引起版本递增而拒绝其合法重放。

仅新命令执行 caseVersion、generation 及事实检查；不匹配时拒绝操作，要求重新核实，操作人文字不能覆盖判定。不同确认 action 的并发也只能一个成功。

若存在可信取消且仅剩价格差异，允许关闭原人工履约 Case、BOrder CANCELLED、平台 FAILED、释放预留。若存在历史成功／提卡／待核资产／身份矛盾则仍人工，不提供强制绕过。

若第 5.4 节的可信未建单判据已满足，允许由真实操作人确认最终履约失败、关闭 Case、BOrder FAILED、平台 FAILED、释放预留；确认权限不能把未知证据升级为可信，不能通过手填“未建单”或次数绕过服务端判定。

本轮实现旧单处置能力，但不执行 `AMP_HS_20261013_01A13312_01` 的真实核实或资金释放；部署及执行需用户分别明确授权。

## 7. 持久化与协议兼容

新增前向 Liquibase，不改已执行脚本，不 clearCheckSums，不批量更新存量订单／资金／Case：

1. BOrder CHECK 增加 60，COMMENT 增加已取消；补供应商终结原因码和脱敏说明，平台终结原因沿状态日志存储并在查询聚合时投影，不创建第二套平台状态真相。
2. 调用审计扩展可选 remoteCode、supplierTraceId、稳定错误原因与实际调用标识；协议事实保留端点及业务发送证据。旧行 NULL 表示未知，不回填假证据。
3. 新增供应链自有 `sc_fulfillment_case_action` 命令审计，保存 actionNo／请求指纹／actor／Case身份／预期与实际代次／执行状态／受保护核实证据／完成摘要／时间；不复用直充频控专用审计表。
4. Case 沿现有 CONFIRM_FAILURE 动作及真实 operatorId／resolvedAt 结案，不新增“无人操作但伪造已结案”状态。

未建单候选及四次有效查询事实须按第 5.4 节持久化，自动流程与人工核实共享同一原单判据；实施计划须确定既有履约事实的存储落点及新增版本，不能用普通日志或人工动作表替代自动流程权威事实。

新核实证据使用显式 schemaVersion、keyVersion、ciphertext，AAD绑定 actionNo、caseNo、operationNo、连接器与供给版本、generation；不改变历史 checkpoint V1 键集合或 AAD。新订单错误事实的持久兼容必须提供缺字段的历史读取语义：缺失即无法证明安全拒绝，不默认无副作用。

实施存储采用 checkpoint V2 的可选未建单候选和 Operation 独立加密结果事实，保留 V1 读取及原 AAD。候选有效次数允许 0～4，人工第 4 次核实只形成待确认依据；每次认领、复制和结果持久化均保留候选与历史保护事实。Case 核实 STARTED＋watchdog、结果＋计数、UNKNOWN＋活动意图清理分别使用真实供应链短事务，外呼不在事务内。密钥版本按现有字符串标识存储为 VARCHAR(64)，不假设数字版本。所有 DATETIME(3) 沿数据库时钟的仓库既有时区语义，不声称 UTC。

实施细化（接管复核）：Operation 独立结果事实复用 `sc_fulfillment_call_log` 的逐次追加记录，不覆盖 checkpoint 的最新观察。追加可选 executionGeneration、evidenceSchemaVersion/keyVersion/ciphertext；新证据 V1 的 AAD 绑定 callNo、operationNo、BOrderNo、连接器/供给版本与代次。有效自动结果和人工 QUERY 结果在相应结果短事务内写入，回调亦保存独立事实；迟到人工结果只留旧 action 诊断，不进入有效计数。关单复核加密记录及各历史 checkpoint，遇历史成功、提卡、资产、身份冲突关闭释放；可信未建单额外核实同原单首次拒绝之后四份不同代次且满足退避的 QUERY 7014。旧调用行缺少证据不能补造有效次数。此复用避免新增第二张调用事实表，不改变原调用日志或 V1 checkpoint 的兼容读取。

2026-10-14 提卡排障补充：结果留证必须接受 `RESULT_UNKNOWN` 且 `rawErrorCode=null` 的合法事实，`remote_code` 保持 SQL NULL；只有已解析接受的事实记录 0，明确业务拒绝保留实际非零码。不得因 Java 条件表达式拆箱空值使结果事务回滚，也不得用 0 或任意占位码替代未知。通过真实 MySQL 的 `HuashengFulfillmentLifecycle.apply` 验证留证与原单 `WAIT_QUERY` 恢复同事务提交、预留保持且无资产交付；不改变恢复配额、资金安全判据或卡型支持范围。本条是留证契约的实现约束，不能单凭本地复现将实机 TAKE 异常归因于该分支，仍须区分实机证据与本地验证。

接管集成修订：人工失败确认在聚合锁内使用核实结果的当前代次通过共同证据检查，成功写入终态后才在同一事务递增代次；不得先递增后使自己的证据失格，也不得复制证据冒充新一次 QUERY。活动冲突 Case 收到正式回调仍须保存不可变事实、保留资产并递增代次使旧核实失效，但不自动结案或交付。候选另外持久化已终止查询序次，退避随每次终止（包括异常）推进，有效 7014 次数独立累计；V2 缺失序次按已有有效次数兼容读取，不补造额外有效查询。最后一次合法认领的第 4 个有效结果可以失败收敛，预算仅阻止下一次认领。

核实执行租约复用既有 `HuashengFlowPolicy.LEASE_SECONDS`（150 秒），不与结果可确认的 5 分钟新鲜度混用。仍持有当前代次的 UNKNOWN／watchdog 终结同事务推进候选查询序次与退避，不增加有效次数；旧代次或迟到结果不能推进新候选。人工取消／失败关单保留受保护核实证据中的原供应商单号。共同资金检查经账户应用服务在当前关单事务内锁定预留并读取最新组合，锁持有至释放与关单提交，避免普通快照检查与动账之间被并发扣款改变。

命令表 CHECK 必须同时拒绝“终结但活动标记仍为 1”和“RECEIVED／STARTED 但活动标记为 NULL”；后者须显式排除 SQL NULL 三值逻辑，不使活动唯一键失效。只在未发布的 066 前向脚本落地，并验证旧 065 升级后历史调用的新事实列仍为 NULL。

管理 DTO 新增可选终结原因、原始供应商状态、实报金额、差异与预留处置摘要；无事实为 NULL，不能把缺失字段解释成未扣款。资金摘要经账户应用服务查询，border 不访问账户／账本 DAL。
