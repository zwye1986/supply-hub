# 平台商品批量上架同步 SPU 与 SKU 修复方案

> 状态：前后端已实现，本地自动化、两阶段复审与跨端整体审阅通过；尚未部署。业务预期来自用户 2026-10-11 明确确认；下文接口扩展、分组事务及回执为本次实现契约，不表示用户已批准部署或业务环境状态已改变。
> 关联设计：`docs/superpowers/specs/2026-09-11-supply-chain-product-center-design.md` §3.1、§4.1.9、§4.1.10。
> 实际排障与联调记录：`docs/集成测试.md` 的“2026-10-11 华晟通新增合作商品选品为空排障”章节。

## 1. 已确认的业务要求与问题

1. “商品上架”指平台商品上架，涵盖 SPU 与 SKU；草稿、主动下架商品均不允许建立后台供应商合作关系，目标 SKU 与所属 SPU 必须同时为 ACTIVE。
2. 商品列表选中 SPU 后点击“批量上架”，用户期望 SPU 与下属 SKU 同步上架，不接受只改变 SPU 后提示整个商品已上架。
3. 用户实际请求为 `spuCodes=[SPU_011]`、`skuCodes=[]`、`targetStatus=10`，返回 `succeeded=[SPU_011]`、`failed=[]`。它只证明 SPU 项处理成功，不能证明 SKU 上架。此前只读查询中 `SKU_011_001.status=0`。
4. 前端 `handleBatchStatus` 固定提交空 `skuCodes`；现有后端只处理显式传入编码，不展开下属 SKU；前端回执校验器也只接受请求中的 SPU。修复必须同时覆盖请求、后端同步范围、事务结果与页面反馈。

## 2. 推荐业务语义与边界

本次实现采用以下业务边界；标题保留为已关联代码注释的稳定锚点。

- 本页面“批量上架”作用于选中 SPU，以及各 SPU 下全部未归档 SKU；包含草稿、已上架和主动下架规格。用户明确执行整商品上架，是该批次恢复下属未归档规格的显式操作意图；确认框须说明会同步恢复已下架规格。
- 已归档 SKU 不恢复；已归档 SPU 继续按状态机拒绝。无未归档 SKU 的 SPU 拒绝整组上架，避免把无规格商品计为成功；复用已有“至少一个 SKU”语义错误并给出可读文案。
- 范围以后台主数据为准，不从 management-page 的当前页、搜索命中或筛选后 skus[] 推断全量规格。后台在操作开始时有界解析成员，组内锁定后再次核验；成员变化时拒绝该组并提示刷新，不能悄悄遗漏新规格。
- 单 SPU 状态接口仍只改变 SPU，单 SKU 状态接口仍只改变目标 SKU。独立状态用于单独下架/恢复；本次整商品批量上架是明确的同步操作，不把它推广成所有 SPU 写入均自动级联。
- 本次同步扩展只用于“批量上架”。批量下架沿用既有 SPU 操作和双亲有效判定：父商品下架立即阻断合作准入及有效可售，不在此次补充要求中自行改变全部 SKU 的独立状态。
- 上架不自动建立合作报价、不自动发布供应商 Offer、不保证商品已具备供货、定价或交易可售的全部依赖。商品主数据两层启用与完整商业可售结论仍须区分。

## 3. 接口方案比较与推荐契约

三种可行路径：

1. 前端逐个读取完整 SPU 详情并填充 skuCodes，复用旧接口：接口改动少，但有多次读取、成员变化窗口及逐实体部分成功，不能保证一组商品同步成功。
2. 给现有批量接口增加显式同步上架模式：后端统一解析成员，可增加组内原子性，并保留旧显式编码模式。推荐此方案。
3. 全局改变 SPU 状态接口或旧批量默认语义为自动级联：会改变既有独立状态调用方的行为，范围超过本次页面诉求，不采用。

本次继续使用 `PUT /supply-chain/products/batch-status`，增加布尔字段 `syncSkuOnShelf`，缺省/false 保留旧契约。新页面“批量上架”固定传 true：

```json
{
  "spuCodes": ["SPU_011"],
  "skuCodes": [],
  "targetStatus": 10,
  "syncSkuOnShelf": true
}
```

true 模式只允许目标状态 ACTIVE，必须有选中的 SPU，skuCodes 必须为空；混用显式 SKU 与同步模式整体拒绝，避免重复计数与归属歧义。false 模式继续允许显式 SPU/SKU 混合编码，并沿用原逐实体事务及回执语义。

HTTP 编码列表保留现有 `@Size(max=200)` 原始列表粗筛契约；服务层同步模式按去重后的 SPU 与展开成员计算实际额度。同步模式在任何状态写入前完成全部选中 SPU 的去重和有界成员解析，展开后 `SPU 数 + 未归档 SKU 数` 不超过现有 MAX_BATCH_STATUS_COUNT（200）；超限整体拒绝，不截断、不由前端自动拆批、不产生状态写入。实现使用技术上限加一的有界读取检测超限，不能先全量物化任意数量规格再检查。请求级输入校验与组级状态/Schema 校验分别处理。

## 4. 分组事务与并发

- 同步模式以“单个 SPU + 其全部未归档 SKU”为一个 REQUIRES_NEW 事务；多个 SPU 组顺序独立执行。一组任一规格不满足状态机、商品类型或 Schema 校验，整组回滚，其他已成功组保持成功。
- 即使 SPU 原本已 ACTIVE，也必须处理其草稿/下架 SKU，不能以父商品幂等成功跳过子规格。
- 每组先锁 SPU 与商品类型，再按稳定主键顺序锁定全部目标 SKU，校验当前成员与执行前解析范围（主键及业务编码）一致。执行前解析与父锁后的成员范围读取均使用剩余额度加一的 LIMIT，逐主键预锁仅接收这份有界范围；锁定后成员变多、减少或归档变化均拒绝，不截断处理。成员变化、缺失或归档变化按业务并发冲突拒绝该组。实施前须核验并补齐会改变子 SKU 成员的既有写入口遵守父行锁顺序，不能只靠读列表声称有并发保障。
- 成员写入口核验：复合创建在新建父行所属事务内插入；复合更新先锁父行，再新增/修改规格；存量单 SKU 创建补齐父行锁；单 SKU 归档必须先读取归属、锁父行，再锁 SKU 并复核归属。税务与非归档单 SKU 状态操作不改变成员，仍以 SKU 行锁串行化与组内锁定。供应链无其它平台 SKU 成员写入口。
- 组内所有校验通过后再修改状态；任一数据库更新失败导致整组回滚。不得通过在外层编排直接自调用现有带注解公开方法来假装获得事务，必须复用/抽取真实事务内状态迁移逻辑。
- ServiceException 计入该 SPU 组失败，失败原因保留具体 SKU 编码及稳定错误码；系统异常按现有终结边界规则传播，可能有之前已提交的其他组，页面不得把整体异常计为全失败。
- 上述“组内原子、组间独立”是同步模式新增语义，替代同步模式下的逐实体事务；原模式的 D1/D2 门禁继续保留，不能直接删除历史回归。
- 修改异常责任、批量日志或事务提交成功日志前，必须遵守全系统日志规范，不能在事务提交前记录商品整组上架成功。

### 4.1 复审修正：显式 NULL 与相交多 SKU 批次锁顺序

- 同步上架须把 `unshelve_mode` 真实写为 SQL NULL；MyBatis Plus 默认 NOT_NULL 不会通过 `updateById` 的 null 属性完成清理。本模式使用局部 `LambdaUpdateWrapper.set(unshelveMode, null)` 的显式状态更新，保持版本条件、更新数量校验及原子事务；不把 DO 全局字段策略改为 ALWAYS，避免其它部分更新意外清空。
- 相交的多 SKU 写批次统一按 SKU 主键升序逐行预锁，再按原请求顺序执行原校验、更新和发布流程，保留输出顺序、业务错误顺序与整批原子性。读取编码对应主键时不持子锁；锁后重新读取行，不使用旧状态快照写入。不得仅凭 SQL ORDER BY 假定锁获取次序，预锁使用逐主键 FOR UPDATE。
- 适用写入口包括批量税务元数据、人工平台批量定价、首版默认定价初始化。复合商品编辑虽已持父锁，但人工平台定价只读取父行，因此复合编辑也必须在父锁之后先按主键升序预锁全部已有规格，再按请求编辑；新增规格在未提交事务中插入且主键单调递增，不存在外部已持其锁的会话。
- 同步上架与复合编辑维持单父行 → 商品类型行 → 子主键升序；类型状态与迁移校验在子预锁之前，Schema 在子预锁之后校验，避免跨父人工定价与复合编辑形成 Type→SKU / SKU→Type 环。税务/人工平台定价不新增父行锁，不改变两层上架准入、定价版本继承或税务仅展示语义。定价锁顺序注记同步到 `docs/superpowers/specs/2026-09-15-generic-batch-pricing-design.md` §5。
- 真实 MySQL 回归须覆盖下架模式清空，以及反序税务/人工平台定价与同步上架并发：反序请求不能转化为反序子锁，不产生死锁，两方均提交。

## 5. 结果与页面交互

同步模式响应增加 `syncSkuOnShelf=true` 及 groups 明细；succeeded/failed 按选中 SPU 组计数，普通模式保持旧计数语义。每组明细包含 spuCode、该次处理范围 skuCodes、是否整组 succeeded；失败组另携具体失败实体编码和原因。未成功组没有“部分已上架 SKU”，组内写入全部回滚。

成功示例（新增契约）：

```json
{
  "code": 0,
  "msg": "",
  "data": {
    "syncSkuOnShelf": true,
    "succeeded": ["SPU_011"],
    "failed": [],
    "groups": [
      {
        "spuCode": "SPU_011",
        "skuCodes": ["SKU_011_001"],
        "succeeded": true
      }
    ]
  }
}
```

- 同步模式 failed 项以所属 SPU 作为 code、entityType=SPU，并保留错误码/错误文案；增加 failedEntityType（SPU/SKU）与 failedEntityCode（具体失败实体编码）定位父商品或子规格。失败组 groups 明细携带同值字段；SKU 失败编码必须属于本组 skuCodes，SPU 失败编码必须等于本组 spuCode。整体组失败时非失败原因的其它成员仍全部回滚。字段同步 OpenAPI/前端类型，不能只靠消息文本匹配错误。
- 前端增加同步模式专用回执校验：必须显式返回模式标识；每个冻结请求 SPU 恰好对应一个组；组成功结果与 succeeded/failed 一致；SKU 编码非空且全批不重复；非法、缺失或旧回执不能宣称同步成功。旧服务忽略新字段并返回旧回执时，也应检测为未确认结果，不自动降级重写。
- 列表勾选仍按 SPU，确认框说明“同步上架选中商品及其全部未归档规格，含此前单独下架规格”。不能仅用当前列表的 SKU 数作为完整操作数量。
- 成功提示按组与规格分别表达，例如“1 个商品及 1 个规格已同步上架”；部分失败按商品组计数，并展示失败 SKU 的具体原因。成功整组规格数从已校验 groups 回执计算。
- 普通下架模式只消费已校验的逐实体成功/失败字段，不读取或遍历额外的 groups 字段；只有已通过同步模式专用校验的分支才能计算规格数量，避免未校验扩展字段导致成功回执呈现中途抛错、成功提示与未知结果同时出现。
- 确认、写请求和刷新期间保持现有 busy 防重入；合法结果、部分失败或结果未知都刷新列表，读刷新失败独立提示，异常不自动重发写请求。
- 复合编辑已有 SKU 未传 status 时保留其独立物理状态，新增 SKU 未传 status 才继承 SPU；显式状态仍按已有契约保存。
- 行内 SKU 上下架已改为目标 SKU 接口，草稿规格可上架，操作列逐规格呈现；页面分别显示父子状态及父未上架的有效阻断。已有 SKU 编辑回填/保存显式保留独立状态；它们不代替本页面整商品批量上架。

## 6. 合作选品一致性

新增供应商品查询始终要求 SPU、SKU 均 ACTIVE，SPU 在分页前过滤、SKU 在候选与明细同时过滤；省略前端 status 参数也不能绕过。普通管理列表保留草稿/下架商品的管理可见性。

创建合作关系保留后台双层状态复核、供货范围、商业条款和未退役重复校验。批量上架后原选品 GET 应出现 SKU_011_001；此时无需用放宽选品过滤来补偿错误状态。

1. 先审阅此方案与商品中心详细设计同步注记，再实现 DTO/领域命令、成员有界解析、组内事务、响应投影及前端模式/回执/交互。
2. 纯逻辑测试：选中 SPU 去重、成员包含草稿/下架/已上架且排除归档、父商品已上架仍处理 SKU、超限拒绝、真/假模式输入边界、故障回执及旧契约回归。

4. 真实 MySQL/Liquibase 集成：SPU 与全部 SKU 同步成功；其中一条失败整组零写入；两组中一组失败不回滚另一组；展开超限全批零写入；成员变化拒绝；锁顺序/并发写入；旧逐实体事务回归。无需新增业务表。
5. 前端执行真实 SFC/API/回执校验测试：新请求明确传同步标识；当前过滤只显示部分规格时不丢范围；草稿规格上架；部分组失败；模式标识缺失/旧回执受控拒绝；busy 防双击与刷新失败不重发；编辑保存保留规格状态。
6. 运行供应链适用纯逻辑、契约、真实 MySQL 与 ArchitectureTest 门禁，以及前端相关测试/类型检查，并在 `docs/集成测试.md` 区分自动化、真实 API 和浏览器验收结果。
