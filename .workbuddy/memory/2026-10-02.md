## 供应商履约参照实现切换：QNM → HUA_SHENG 修改方案

业务决定把供应商履约的首要参照从 QNM（奇那梦，明文 MD5 + 一段式）切换为 HUA_SHENG（华昇，AES-CBC + RSA-SHA512 + token + 两段式下单 + 异步回调 + 主动取券 + 错误码三级分类）。语义：HUA_SHENG 作为新主参照完整落地，QNM 代码保留作多供应商扩展性验证。

### 产出
- 设计文档：`docs/superpowers/specs/2026-10-02-huasheng-fulfillment-adapter-design.md`（**v2 修订版**，含代码/DDL/测试/迁移/风险；v1 已被 v2 取代）

### v1 → v2 评审发现（v1 存在 P0 缺陷，勿再沿用其错误前提）
- **checkpoint 是死代码**：`OperationOutcome.nextCheckpoint` 与 `sc_fulfillment_operation.checkpoint_ciphertext` 从未接线（main 源码 `setCheckpointCiphertext` 零出现），`handleAccepted` 不写库。v1 误以为"可复用现有 checkpoint 机制"。
- **`ck_sc_fulfillment_operation_kind` 有 CHECK 约束**（`004-...sql:461`），v1 §5.2 误判"无 CHECK 约束"，新增 operation_kind 会被直接拒绝。
- **`ck_sc_b_order_quantity CHECK (requested_quantity = 1 AND fulfilled_quantity IN (0,1))`**：`num>1` 会在回调落库时违反 CHECK 导致崩溃，必须在协议层显式拒绝。
- **`extraParameters` 恒为空**：`FulfillmentOperationTicketFactory:62` 硬编码 `Map.of()`，传递链断裂。
- **`OperationTicket.secretKey` 单字段**撑不起 HUA_SHENG 三密钥（appSecret/privateKey/callbackPublicKey）。
- **ArchUnit 无需放宽**：`admin_controllers_do_not_depend_on_supplier_adapter` 仅约束 `..interfaceapi.admin..`，新建 `..interfaceapi.callback..` 不在范围。

### v2 关键设计决策
- **AD-1**：两段式接入**既有** `SupplierOrderLifecycle.continueAfterTrustedRejection`（`:133-137`）+ `validateContinuation`（`:458-478`，含 `sameBOrder` 同 BOrder 内 `sequenceNo+1` 递进能力），不自建编排。需扩展 `isRechargeOperation`（`:487-490`）识别新 step，并给 `handleAccepted` 增加下一 Operation 串联。
- **AD-2**：checkpoint 由 `handleAccepted` 用 `EnvelopeCryptoPort.encrypt(aad=operationNo|bOrderNo|step)` 落库；恢复在 `FulfillmentOperationExecuteHandler`（已注入 `EnvelopeCryptoPort`）解密，经 ticket 新字段 `checkpointPlaintext` 传适配器，保持适配器无加解密依赖。
- **AD-3**：新增 `sc_credential_set` + `sc_credential_item` 两表 + `CredentialProvider.resolveSet` + `OperationTicket.CredentialMaterial` 记录类型；`secretKey` 保留兼容 QNM。
- **AD-4**：`HuashengTokenManager` 放应用层（不占 supplieradapter），新增 `TokenAuthenticatedExecutor` 子接口，token 经 `extraParameters` 注入。
- **AD-5**：`sc_supplier_connector_version` 新增 `extra_config JSON` 列打通 `extraParameters` 传递链。
- **AD-6**：一期固定 `num=1`，协议层拒绝越界（`HS_NUM_UNSUPPORTED`），不动 DDL quantity 约束。
- **建议**：取券复用 `FULFILL` + `TAKE_CARD` step（而非新增 `TAKE_ASSET` kind），可让 `operation_kind` CHECK 约束零改动，DDL 仅剩 `capability_code` 一处 ALTER。

### 关键路径
T8（三密钥）→ T9（extraParameters）→ T10（checkpoint 落库）→ T11（多步骤编排，风险最高，触及资金与频控边界），建议先技术预研再实现。

### 关键调研结论
- supply-hub 现有六角架构（`OperationExecutorPort` + `AdapterMetadata` 注册 + `OperationTicket/Outcome` + `sc_fulfillment_operation.checkpoint`）无需破坏，HUA_SHENG 作为新适配器接入。
- 旧实现位于 `/Users/mac/Documents/codeSpace/cardshop` 的 `huasheng` 包（11 个类），核心：`HuashengCrypto`（AES+RSA）、`HuashengClient`、`HuashengTokenManager`、`HuashengErrorCode`（30+ 码三级分类）、`HuashengSupplierTradeServiceImpl`（两段式编排）、`HuashengCallbackService`（多重防护）。
- HUA_SHENG 与 QNM 关键差异：签名（MD5→RSA-SHA512）、加密（无→AES-CBC）、鉴权（userkey→token）、下单（一段→两段 placeOrder+confirmOrder）、取券（同步→主动 takeCard）、回调（明文表单→密文 hex）、错误码（散落→枚举三级分类）、补单（无→指数退避）。
